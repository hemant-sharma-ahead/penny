70Bank/card merge suggestion is falsely confident across 2+ same-bank accounts
suggestCardAccountMerges() matches purely by normalized bank name and picks the first non-card resolution sharing that key — with zero disambiguation when the user already has 2+ accounts for the same bank (e.g. two SBI accounts). The row's own "Matched account" dropdown already lists every account and already works — this is only about the confident-vs-ambiguous state the row is presented in.
Plan (from the doc): when 2+ existing accounts share a bank key, treat the match as genuinely ambiguous rather than confidently picking the first one — flag the row as needing a manual pick among the same-bank candidates instead of pre-filling a specific guess. Needs a new "ambiguous, pick one" visual state for the row.

Confirmed — final direction: the hybrid. The from→to header (source account → chosen Cash account) is always visible regardless of group size. Rows render inline up to TileRowList.tsx's own existing >4-rows threshold — a typical small withdrawal group (≤4 rows) never needs anything more than what's already inline, which is exactly what fixes the plan doc's original complaint (per-row amounts being invisible). Once a group exceeds that threshold, the extra rows move behind a "See all" affordance that opens the exact same popup/modal shell used for item 75 below — not the side-by-side duplicate-pairing content (these are withdrawal candidate rows, not duplicate pairs), just a plain date+amount list, scrollable, same centered Modal.tsx primitive. This avoids both the original "always-expanded" option's risk of a huge card for a long transaction history, and the "always-collapsed" option's extra tap even for the common small-group case.
Resolved: the hybrid threshold/behavior above is locked in — no open choice remains between "always show rows" vs "always collapse" vs hybrid. One item carried over unchanged from the previous round, still worth a real-file check before implementation is called done (not a design decision, just a data-shape edge case): a cash-withdrawal group is built from rows sharing one CSV category (e.g. "ATM Withdrawal"), not one CSV account — a file mixing multiple bank accounts could in theory produce a group whose rows span more than one source account. The mockup above assumes the common case (one shared source account, resolved the same way TransferPairCard.tsx already resolves a leg's real account); if a real file turns up a mixed-account group, the "from" side needs a documented fallback (most likely "Multiple accounts", mirroring TransferPairCard.tsx's own raw-name-fallback pattern).
