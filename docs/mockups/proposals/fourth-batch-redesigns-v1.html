Recommendation: ship the starred option in each section — they're the three that scale best once the app has real transaction volume, not just the ones that look nicest in a gallery.
  • §1 — Tightened rhythm. The literal-merge ask genuinely doesn't hold up at this card's real width (270–290px) — it needs hard name truncation and sub-legible number sizes even before item 33's decimals land, and gets worse once they do. Tightened rhythm keeps the name legible (it carries real information — which account) while still reading as one glanceable block, and is completely unaffected by the 2-decimal change since the fit risk is in the numbers' width, not the vertical gap.
  • §2 — Smart pre-resolve + single review. This is the one that actually answers "why do people fall back to some apps again and again" (DESIGN_GUIDELINES.md §1) — a clean file should feel like 2 taps, not a forced tour of 5-6 screens that all say "yes, this is fine" back to back. Stage consolidation is the safer fallback if the smart-review screen's real-data cases (partial auto-resolution, a genuinely messy file) turn out messier than this mockup's clean example — worth prototyping against a real large file before committing, same way the original redesign's 9,384-row sample file surfaced things a clean example wouldn't.
  • §3 — Persistent scrub bar. Cashew and every other fast personal-finance app converged on this for a reason — "last month" and "this month" are the overwhelming majority of real taps, and those should never cost a modal. The flat list is a reasonable fallback if the scrub bar's screen-space cost (a whole extra row, always visible) turns out to be a bigger tradeoff than expected once seen against the real Transactions screen's already-busy filter bar.

Judgment calls & open questions for review

  1. §1 — which numbers demonstrate the decimal-fit risk. formatCompact falls back to plain formatCurrency only under ₹1,000 (checked packages/core/src/lib/formatters.ts) — a big-balance account (HDFC, compact notation) is untouched by item 33's decimal change either way; the real fit risk is specifically a low-activity account (Cash, here) whose values stay under ₹1,000 and go from e.g. "₹450" to "₹450.00". Used a two-account pair on purpose so both cases are visible side by side, rather than picking amounts that make the concern invisible.
  2. §2 — "Smart pre-resolve" example is deliberately a clean-ish file. 3 accounts, 43 categories with only 2 needing review. A messier file (more unmatched categories, several ambiguous accounts) would show a more heavily-expanded screen — still fewer taps than today's forced 5-6 screens, but the "2 taps" number in the tap-line is the best case, not a guaranteed one. Flagging so it isn't read as an overclaim.
  3. §2 — tag-suggestion widget placement. Per the task, shown as a fixed addition wherever a categorization step renders (here: on the IOU-suspect tile in the smart-review option, since that's the one place a tag most plausibly matters — "loan", "vacation" etc.) rather than on every single tile, to avoid cluttering an already-dense review screen. Worth confirming this is where the port should land, vs. every tile getting the same affordance.
  4. §2 — stage-consolidation's internal layout. Modeled "Resolve mappings" as one combined bucket list mixing account-rows and category-rows under shared Needs-Review/Ready buckets, since both already use the identical BucketCard shell today. An alternative would keep them as two visually distinct sub-lists within the one stage instead of fully interleaved — didn't build both, flagging as a real choice if this option is the one that ships.
  5. §3 — scrub bar's visible window size. Mocked 5 visible chips (Apr–Aug) as a representative width for a ~280px phone frame; the real implementation should size this to whatever fits the actual device width rather than a fixed count. Arrow-scroll step size (one month vs. a wider jump) is also unconfirmed — modeled as scrolling by roughly one chip-width per tap.
  6. §3 — "Jump to…" and flat-list's exact history depth. Used the plan doc's own "last 24 months" for the flat list; the scrub bar's modal fallback reuses the SAME current year+grid modal rather than inventing a third picker style, on the theory that once a user needs "further back than visible," the existing grid's year-jump is actually the more useful tool, not a limitation to route around twice.
