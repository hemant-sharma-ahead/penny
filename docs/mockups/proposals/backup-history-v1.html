Backup History — This device & Google Drive (v1)

Scope: apps/mobile/src/features/backup/AutoBackupCard.tsx. Adds a per-destination Backup History popup (last 20 backups, Download/Delete per entry) reachable by tapping the existing "Last backup: <date>" caption in the This device and Google Drive panels — iCloud is untouched (not implemented natively, out of scope per the decided plan). Restore stays "always restore the latest" — no per-entry restore action anywhere below, by explicit decision. Nothing here has touched app code yet.

scope check — backend/data-model dependency, not just UI Read packages/core/src/core/sync/providers/googleDriveProvider.native.ts and localBackup.native.ts before drafting this: today neither destination keeps more than one backup. Drive's pushImpl() always finds-or-creates one fixed appDataFolder file (DRIVE_BACKUP_FILE_NAME) and PATCHes it in place; the on-device silent snapshot is similarly a single rotating file, and "Back up now" on This device is really an on-demand share (exportToDevice()), not a saved entry at all. A prior mockup (backup-restore-redesign-v1.html's "Future ideas" section, 2026-08-21) explicitly locked a "Backup history" concept as not buildable today for exactly this reason. This proposal is the UI/UX layer for the now-decided feature — real implementation still needs a storage-model change first: each backup write (auto or manual) must create a new, separately-addressable, timestamped entry per destination (a new local file per snapshot; either a new Drive file per backup or a metadata-tracked history alongside the one Drive blob) plus retention pruning to the last 20. Flagging so this isn't mistaken for a pure-copy/UI change — it's a real precondition, not a nice-to-have.
cross-platform check apps/web-react/src/features/backup/AutoBackupCard.tsx has no history concept of any kind — just the same single status caption mobile had before this change. Since apps/web-react is frozen (CLAUDE.md — no further changes, historical reference only), nothing here needs mirroring there. This is a mobile-only capability going forward, same as the foreign_blob banner and navigation-lock work already mobile-only per that file's own doc comment.
duplication check — two popups is the deliberate design, not an oversight Per the decided scope: two separate History popups, one per destination, opened independently from each panel's own caption — not one combined tabbed modal. This is intentional, not "one capability implemented twice" in the sense §1 warns about (that rule is about the same action reachable from two different controls) — local and Drive are genuinely different storage models with different constraints (Drive needs network/auth, local doesn't), so their history lists, empty states, and delete semantics are already different underneath. Reusing one modal component for both (as this mockup does, just with a destination prop) is the correct "keep shared controls in sync" move without forcing a false single-IA on two genuinely different things.
new pattern, flagged as such SwipeableRow.tsx's only current caller (TransactionsTab.tsx) has zero static affordance that a row is swipeable — no hint icon anywhere in the real app today, confirmed by reading that file in full. Per the brief's own request for "a static/at-rest state so the swipe affordance isn't the only way to discover it," this mockup adds a small trailing ti-chevron-left hint (tertiary, low-opacity) to each history row — a genuinely new visual convention, not something already established elsewhere, so calling it out explicitly rather than presenting it as if it already existed. Worth deciding once, here, whether it's worth adding to TransactionsTab.tsx's rows too for consistency — out of scope for this task, noted for a future pass.

Reverse-chronological list · swipe-to-reveal Download/Delete · empty state

Each row: date/time prominent, file size + Auto/Manual badge as the secondary line, swipe-left reveals Download (theme.info) and Delete (theme.danger) — the same two colours TransactionsTab.tsx's own swipe actions already use for Copy/Delete. A small trailing chevron hints the row is swipeable (see the "new pattern" finding above). Component reuse, not a new shape: the popup itself is Modal (title + built-in × close, scrollable body) — no new modal primitive. Each row is a SwipeableRow with exactly two SwipeActions ({ icon: 'ti-download', label: 'Download', color: theme.info }, { icon: 'ti-trash', label: 'Delete', color: theme.danger }) — identical shape to TransactionsTab.tsx's own actions array, just a different two actions. Delete opens the existing ConfirmDialog (confirmVariant="danger"), same component AutoBackupCard.tsx already uses for "Overwrite Drive backup?" — no new dialog shape anywhere in this proposal.

Drive-specific framing: the account chip under the title ("synced from Google Drive") is the only structural difference between the two popups — it answers "whose Drive am I looking at" without repeating the account row already shown in the panel behind it. Nothing else about the list/row/empty/delete states differs by destination.

Retention note placement: "Showing your most recent backups (up to 20 kept)" sits once, at the top of the list, in tertiary text — no progress bar or counter widget, per the brief. It's shown regardless of whether the list is actually at the 20-cap yet (reads fine at any count, and avoids a separate "you're approaching the limit" state that isn't needed for something with no real cost to the user, unlike a storage quota).

Notes & open questions for review
Needs a small new helper: no formatBytes/file-size formatter exists anywhere in this codebase today (checked apps/mobile/src/lib/ and packages/core/src/lib/) — real implementation needs a tiny new util (e.g. "3.6 MB" / "820 KB") alongside the existing formatDateTime() (packages/core/src/lib/date.ts) already used for the row's date/time line.

Deliberately not shown: per the decided scope — no item/transaction count per entry (not tracked today), no per-entry restore action (restore stays "always restore the latest"), no combined tabbed popup (two separate, destination-scoped popups), no changes to the iCloud row/panel.

Worth deciding before implementation, not blocking this mockup: whether "Download" on a local entry means share-sheet (matching exportToDevice()'s existing behaviour) or a silent copy somewhere the user can find later — this mockup's label just says "Download" either way, but the underlying action differs from Drive's "fetch this specific historical file," which is a real, currently-nonexistent Drive API call (today's provider only ever reads/writes the one fixed file).
