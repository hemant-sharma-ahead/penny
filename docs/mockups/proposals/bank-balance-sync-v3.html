The two half-tables need no new core computation — the April-onward half is literally today's already-fixed computeCheckpointDiagnostics() call, untouched. The January–March half is the same function called a second time, scoped to just those rows, with the backfill's own implied opening balance. Whether ① is even listed depends on a real, checkable fact: does a genuine uncovered gap exist between the two statements' own date ranges (detectCoverageGap already computes this) — if the statements are back-to-back with no gap, ① is impossible by construction and shouldn't be shown at all.

A second, more serious bug this exposed — on-device repro, 2026-08-09 Tested end to end: chose "Keep ₹50,000, flag" → later re-imported the corrected Jan–Mar statement (real ₹35,000 salary instead of the erroneous ₹37,000) → the review screen correctly matched 6 of 7 rows and flagged the stale ₹37,000 entry for deletion → deleted it, recorded the correct ₹35,000 in its place. At this point the ledger is genuinely fixed — a fresh check would show ₹0 diff at the boundary. But the account still shows "Re-open ›", and reopening it still shows the exact same stale ₹52,000/₹2,000 numbers from before the correction.

Root cause, confirmed in accountVerification.ts:146: unlike checkpoint-mismatch (line 131, computeCheckpointDiagnostics() — walks the CURRENT transactions fresh, every single call), anchorDisagreement is a raw pass-through of whatever got written to Account.anchorDisagreement once, at the original import's commit time. Nothing anywhere re-derives or invalidates it afterward — not a later corrective import, not an edit, not a deletion. It behaves like a permanent verdict when the design intends it to behave like a live check.

Recommended direction (bigger than originally scoped, but the right fix): stop persisting the computed half of this finding at all. Keep only the historical fact worth remembering permanently — the OLD anchor's own independently-established value/date (₹50,000 @ 2 Apr) — and re-run the actual comparison against current transactions live, every time verification status is computed, exactly like checkpoint-mismatch already does. Once live, a corrective import (like the one just tested) would make the finding disappear on its own the moment the ledger actually reconciles — no manual "Update"/"Keep" dance needed unless a real disagreement still exists. This also folds in cleanly with the separate write-path bug from before (the anchor never moving back to the true earliest transaction date) — both are really the same underlying issue: something about this feature was designed to compute once and freeze, in a codebase where every sibling mechanism (checkpoints, coverage gaps) recomputes fresh from source data every time.
