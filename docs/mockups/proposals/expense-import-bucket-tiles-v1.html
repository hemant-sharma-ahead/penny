Recommendation: ship all three changes together as one pass. They compose into the same screen and share groundwork — collapsing CategoryTile into a bucket card is what makes the "Staged" bucket card actually scannable (three peer cards of already-busy inline tiles would be worse than today, not better); and removing the Accounts/Preview mutual exclusion only matters once Preview itself is calm enough to sit open alongside Accounts without the screen feeling crowded, which the bucket-card collapse also buys you. If forced to stage, do #1 (bucket card + modal) first — it's the one with real behavior change (moving 4-way resolution into a modal) and the most implementation risk; #2 and #3 are comparatively mechanical (a state removal, and a label/wrapper swap) and easy to layer on after.
Open judgment calls — flagging for your decision:
  1. Tag field hidden for "Skip" (§3): I hid the tag field entirely when Skip is selected, since tagging a transaction that won't be imported has no effect. An alternative is to keep it visible but disabled, so the layout doesn't visibly shift between kinds — I judged hiding it as the more honest "this field doesn't apply" signal, but it's a real tradeoff.
  2. Footer button copy for "Skip" (§3): I kept it as "Apply to N transactions" for consistency with every other kind, even though "Skip 3 transactions" would be more honest about what actually happens. Kept uniform per the spec's stated footer convention, but flagging since it reads slightly oddly for this one kind.
  3. "Needs confirming" badge color (§1): reuses theme.warning (amber), same as every other attention-tinted surface on this screen (the tile's own border, the old gate chip). Worth double-checking it doesn't read as visually identical to the tile's own "attention" background tint at a glance — if that's a concern, a distinct icon (e.g. ti-help-circle instead of ti-alert-triangle) could differentiate "needs confirming" from "needs categorizing" more clearly.
  4. Auto-expand rule when "Needs your input" is empty (§5): mirrors ReviewStep.tsx's existing Accounts/Preview convention (auto-expand whatever needs attention, else the "next" thing) — when nothing needs input, I did NOT default-expand "Staged" instead; all three collapse. Worth confirming that's the right default vs. auto-expanding Staged as the reasonable "nothing to fix, look here" behavior once everything's clean.
  5. "Looks good, use this" button style (§3): styled as a warning-tinted pill inside a dashed warning-tinted banner (matching the badge/tile's own warning tone), distinct from the modal's primary "Apply" button at the bottom. An alternative is making it look like a second primary action — I chose the quieter treatment since it's a shortcut for one specific starting state, not the modal's main action.

Why bucket CARDS in one scroll, not tabs (deliberate departure from a literal reading)

The request's framing — "a staged tab to look at one final time before import" — could be read literally as introducing a tab/navigation control. This mockup deliberately does NOT do that. Reasons:

  • This app's import flows don't use tabs anywhere. Bank Import's four buckets (Matched / Possible / Not-yet-logged / Lone-Wolf) — the exact precedent this whole proposal is porting from — are peer collapsible sections in one scroll, never a tab bar. Introducing a tab paradigm here would be a new, unprecedented interaction model for this exact screen family.
  • docs/DESIGN_GUIDELINES.md §2 states the navigation principle directly: "Full-screen, single-scroll over hidden navigation. Prefer a single scrolling page with grouped sections over tabs / sub-screens / drawers that bury content or add clicks." A tab control here would bury "Needs your input" and "Already imported" behind an extra tap exactly when the user most needs to see all three at a glance (e.g. realizing mid-review that something in "Staged" actually needs fixing).
  • The actual need — "look at what's staged before importing" — is fully satisfied by a bordered, independently-collapsible bucket card. It reads as its own distinct section (not just a text label), can be expanded for a final look, and sits directly alongside its siblings with zero navigation cost — nothing the request needed is lost by not using tabs.

Where each piece actually lives (implementation-facing, for when this is approved)

  • Bucket-card collapse (§1/§2) — CategoryTile.tsx gains its own collapsed/expanded state for the WHOLE resolution surface (not just the row list, which already has this). The kind picker/tag box/create-transfer fields/gate block all move out of the tile and into the new ImportCategorizeModal; the tile itself renders only the header + (if expanded) TileRowList + the always-visible footer button.
  • ImportCategorizeModal (§3) — new file, sibling to CategoryTile.tsx, structured like BulkCategorizeModal.tsx (same Modal/Banner/footer conventions) but built around CategoryAction's 4 kinds instead of Bank Import's 2. Reuses CategoryPickerModal (existing kind), the existing create-fields/transfer-fields JSX currently inline in CategoryTile.tsx (moved, not rewritten), and a new "Looks good, use this" shortcut only rendered when the tile's CURRENT suggestion is already kind: 'create' and undecided.
  • ReviewStep.tsx (§4) — delete the manualSection-forces-exclusivity logic; replace with two independent expanded booleans (one per section), each still defaulting per the existing auto-expand rule (Accounts open until resolved, then Preview) but no longer collapsing its sibling when toggled.
  • Three peer buckets (§5) — PreviewSection.tsx's three glabel blocks (Needs your input / Ready / Already imported via DuplicatesBucket) become three Views with their own local expanded state and the bordered-card + dot-header treatment shown above — same visual weight as the existing "Linked transfers" card just above them in the same file. "Ready" renames to "Staged — ready to import" in copy only; no data-shape change.
