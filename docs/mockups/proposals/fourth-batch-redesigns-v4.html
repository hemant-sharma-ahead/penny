4th-batch UI/UX redesigns — v4 (dropdown-first Accounts/Categories + scrub-bar fixes)

v4 of fourth-batch-redesigns-v3.html, after a third round of direct feedback — refinements only, no new structural galleries. §1 is FINAL, carried over unchanged (layout + real logos both already approved). §2/§3 push the "one capability, one control" simplification one step further: the per-row/per-tile kind-picker is gone entirely — a dropdown IS the primary control, pre-filled with the smart best guess. §4 fixes a mockup-fidelity issue (a browser scrollbar the real RN ScrollView would never show) and restores one-tap access to the unfiltered "All time" view. Re-grounded this session in AccountsSection.tsx, ImportCategorizeModal.tsx, and MonthPickerModal.tsx.

What changed since v3 — read this first.
  • §1 — unchanged, final. Copied over exactly as approved (stacked-icon layout, real HDFC/ICICI/Axis logos, honest placeholder badge for the other 9). One addition: a closing note that the user wants this same real-logo treatment rolled out app-wide wherever an account icon renders — not a new mockup, just a scoped follow-up task since the same components already read account.icon/account.color today.
  • §2 — the 2-pill row is gone. "Map Existing" is no longer a separate label/pill you tap before you can see a dropdown — the dropdown (pre-filled with the best-guess account, or an honest blank placeholder when there isn't one) is the row's one primary control. "Skip" is the only other action, shown as a small text/icon link beside it. Shown as an explicit before (v3's pill row) vs after (v4's dropdown-first row) comparison. "+ Create Account" and the Needs Review/Ready/Skipped BucketCard badges are unchanged.
  • §3 — same philosophy, Transfer kept distinct. A category dropdown (best-guess prefilled) is now the tile's primary control. "Mark as Transfer" and "Skip" are demoted from a 3-way segmented pill row to two small secondary buttons sitting below the dropdown — Transfer still expands its own mandatory destination-account field when chosen, since (confirmed again in ImportCategorizeModal.tsx) it can't collapse into an implicit default the way "existing" could. "+ Create Category", the counterparty chips, and the real bucket titles are unchanged.
  • §4 — two fixes, no structural change. (1) The scrub strip's browser-native scrollbar — an HTML mockup artifact, not something a real RN ScrollView shows — is hidden; the strip still scrolls, just without a visible track. (2) A pinned "All" chip now sits before the scrollable strip, always reachable in one tap, restoring access to the unfiltered all-time view the always-a-month-active redesign risked losing. The "Mon" vs "Mon YYYY" rule is also resolved: year shows whenever a chip's year isn't the real current year (2026), regardless of what's selected — simpler than the v3 selected-year-relative interpretation.

Recommendation: ship all four sections as shown here.
  • §1. Already approved, ship as-is. Track the app-wide logo rollout (Accounts list, account picker in the expense/income/transfer form) as a follow-up implementation task, not a new mockup — it's the same icon-resolution logic applied to components that already exist.
  • §2 & §3. Dropping the named "Map Existing"/pill step is the right final simplification — once "create" moved to a screen-level button in v3, the remaining pill row only ever really chose between "existing" and "skip", and "existing" already had a dropdown of its own once selected. Collapsing that into "the dropdown is the row" removes a tap and a redundant label for the 99% case, while Skip stays exactly one clearly-secondary action away. Transfer correctly stays a first-class secondary button in §3, not swept into the same collapse — it has real structural requirements (destination account) a dropdown default can't express.
  • §4. The "All" chip closes a real regression risk: defaulting to a single active month (for performance, per docs/plans/real-device-testing-pass.md item 42) is the right call, but only if the classic "see everything" view stays one tap away — pinning it outside the scrollable strip, rather than making it chip #1 that could scroll out of view on a long history, is what actually guarantees that.

Judgment calls & open questions for review

  1. §2 — "no confident guess" placeholder demo. Added a 4th source row, "Unknown A/c 9981", with no smart-match candidate, specifically to demonstrate the blank-dropdown / Needs-Review path the spec called for — it wasn't in v2/v3's row set. Purely additive for demonstration; doesn't change the 3 existing rows' behavior.
  2. §2 — merge/fuzzy-match sub-features not re-modeled here. The real AccountsSection.tsx also has a same-account-written-differently fuzzy-merge suggestion and a card→account merge suggestion, both with their own accept/dismiss affordances. This mockup's scope (per this round's ask) is specifically the pill-vs-dropdown row structure — those merge features are orthogonal and unchanged by this proposal; flagging so a real implementation doesn't assume they were designed away.
  3. §2/§3 — is a pre-filled dropdown ever "wrong" without the user noticing? Removing the explicit "Looks good ✓" confirm step (v3's matchcard) means a confident best-guess is treated as already-accepted the moment it's shown, not after an explicit tap. This is the intended simplification (dropdown selection itself is the decision), but it does mean a wrong high-confidence guess ships silently unless the user notices and changes it — worth a real one-time toast/undo affordance in implementation, not just relying on the dropdown being visually obvious.
  4. §3 — secondary-button toggle behavior. Modeled "Mark as Transfer"/"Skip" as toggles: tapping an already-active one reverts the tile to category mode. Not explicitly specified either way in the ask; this seemed like the least-surprising behavior (no dead-end state with no way back to the dropdown) but flagging as a judgment call.
  5. §4 — earliest-transaction-date scan. Unchanged open item from v3 — no existing helper computes the real floor date; still illustrated with a fixed Nov 2014 floor rather than a computed one.
  6. §4 — "All" chip and the calendar-icon modal. The calendar icon still opens MonthPickerModal for jumping to a specific month; it doesn't also expose an "All time" option inside that modal, since "All" living outside the modal (always one tap, no dialog) is the whole point of pinning it in the scrub bar itself. Flagging in case a future request wants both entry points to carry it.
