Groups redesign — Phase 3, real-device testing pass

The five UI-affecting items from docs/plans/real-device-testing-pass.md's Phase 3 — grounded in the real current apps/mobile/src/features/groups/*.tsx screens (checked, not designed against memory). Reuses existing patterns throughout: the centered Modal/ConfirmDialog shell, IouView.tsx's Archived-row icon-button pair, SegmentedControl, Banner, and item 11's wizard-step chrome (WizardProgress.tsx). No new UI primitive is introduced. apps/web-react's equivalent screens were checked for every item and carry the identical gap in each case (see closing notes) — it is frozen, so nothing here proposes touching it.

① Feed row actions ② Delete-when-empty ③ Write-off marking ④ Promote to Group ⑤ Static members
1Feed row actions — edit/delete/flag (item 9)
The recorder gets a direct edit/delete affordance on their own row; another member gets a lighter "flag as not needed" that notifies the recorder rather than unilaterally removing their entry.
GroupDashboard.tsx's FeedRow (line ~235) renders a shared_expense row with zero action affordance today. Chose a direct trailing icon-button pair over both a swipe gesture and an overflow/kebab menu: no overflow-menu pattern exists anywhere in this app (checked), so inventing one would violate "reuse patterns the user already knows"; SwipeableRow exists but is Transactions-tab-only today, and Phase 5 of this same plan doc already earmarks "extend SwipeableRow to … Group feed rows" as its own future item — designing it here would duplicate that scope rather than build on it. The closest real precedent is IouView.tsx's Archived-person row, which already solves "a list row needs 1-2 lightweight actions" with plain trailing icon buttons, no menu. expense_edit/expense_delete event types and their fold-engine handling already exist in groupSync.ts — only the UI callers are missing.

Recommendation: ship all five, but treat them as three tiers of readiness. §2 (delete-when-empty) and §5 (static members) are the most self-contained — small, additive, low product-ambiguity — build those first. §1 (feed actions) and §3 (write-off) both need a small, genuine schema addition (a flag event pair; a settlement kind field) before the UI here means anything — worth confirming those additions with whoever owns groupSync.ts/split.ts before implementation starts, not just inferring them from this mockup. §4 (promotion) is the one with real open product questions below — I'd sequence it last and treat the wizard copy as a strong first draft, not a final spec, until those are resolved.
  • Cross-platform: checked apps/web-react/src/features/groups/GroupDashboard.tsx and GroupMembersModal.tsx — both carry the identical gaps (no feed-row actions, no delete-group, no write-off, no placeholder members, no promotion bridge). Since apps/web-react is frozen, none of this proposes touching it — flagging only because the platforms already agree here (both lack it), which is itself worth recording rather than assuming.

Judgment calls & open questions for review

  1. §1 — how "notify the recorder" actually works. This app has no push-notification infrastructure (local-first, pull/sync-based). I designed the flag as a durable, sync-carried state — the recorder sees it next time they open/sync the group (the same model every other Group update already uses), plus a top-of-dashboard Banner so it's not buried in a long feed. If "notifies" was meant to imply something more immediate (a badge on the tab bar, a daily digest), that's a bigger addition than a UI mockup should silently decide — flagging explicitly.
  2. §1 — new event types needed. A flag needs at least two new GroupEventTypes (raise/clear) or an equivalent field on the existing payload — not decided here on purpose; this is a mockup, and that's a real schema/fold-engine design question for whoever implements it, not a UI one.
  3. §2 — "Leave group" moved into the new Danger zone card. Not explicitly asked for, but it's the only other destructive action on this exact screen and DESIGN_GUIDELINES.md §2 already mandates isolating destructive actions this way — flagging as a bundled consistency fix rather than scope creep, easy to drop if it should stay a separate follow-up.
  4. §3 — settlement kind default. Assumed existing/old settlement events implicitly mean kind: 'repayment' for backward compatibility (no migration needed, just an optional field). Confirm that's an acceptable default rather than requiring a backfill.
  5. §3 — can a write-off be reversed? Not designed here. A real settlement has no "undo" today either, so parity would say no — but a write-off is more of an admin/judgment call than a payment event, so a "reopen this balance" affordance might be worth a follow-up if it comes up in practice.
  6. §4 — what exactly gets seeded. Assumed 1:1: each historical LedgerEntry becomes one shared_expense event (lent/borrowed), and pre-existing settlement entries in that ledger become settlement events too, so the new Group's balance starts at the same net the personal ledger ended at. This is a real design decision with cost/complexity implications, not just a UI detail — worth explicit confirmation before implementation.
  7. §4 — does promotion auto-send the invite, or just create the link? Designed the narrower reading — Step 3 only generates the invite link (mirrors today's manual "Create invite link" flow); actually getting it to Priya (share sheet, copy) is a manual follow-up from the new group's own Members screen, not something this wizard automates. Flagging in case the intent was closer to "auto-invite via her known phone number," which would need a real messaging integration this app doesn't have today.
  8. §4 — is promotion truly one-way? Per the plan doc, yes (archived, not deleted) — but "can I ever unarchive the personal ledger if the Group idea doesn't work out" is a real user question this mockup doesn't answer. Leaning "no, by design" (the Group is now the source of truth) but flagging since it's a permanent decision presented after only a 3-step wizard.
  9. §5 — does a placeholder member need any settlement-recording capability of their own? Designed as "no" — purely a name in the split, with every action (splitting them in, settling their balance) performed by a real member on their behalf. If the intent was closer to "someone hands me their phone to confirm a settlement," that's a materially different (shared-device) flow not designed here.
  10. §5 — can a placeholder be upgraded to a real member later (e.g. once they install the app), keeping their balance history? Not designed here — mirrors the same open question the personal-IOU Person→Group bridge (§4) already raises, just in the other direction. Worth deciding once, consistently, for both.
