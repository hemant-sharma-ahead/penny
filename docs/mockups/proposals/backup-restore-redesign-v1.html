Backup & Restore redesign — layout options (v1)

Scope: apps/mobile/src/features/backup/BackupPage.tsx + AutoBackupCard.tsx. Grounded in the real current screen (read in full before drafting this — see the Current (today) section below, which mirrors the actual code, not an approximation). Three genuinely different structural options for how simplified restore copy + honest in-progress state + Cashew-style Drive account management come together on one screen, plus a separate, clearly-labelled Future ideas section for what a single-Drive-blob model genuinely can't do today. Nothing here is final — no app code has been touched.

duplication check — clean Unlike the 2026-07-27 incident this skill explicitly warns about, mobile's Backup screen is already consolidated — BackupPage.tsx has exactly 3 cards (Automatic backup / Restore / Reset), and AutoBackupCard.tsx's own doc comment confirms the standalone "Export backup" and "Back up to Google Drive" cards were already folded into its destination tabs. This redesign only enriches the existing Drive tab's content (account identity, toggle, frequency) — it does not reintroduce a second place that does the same thing, and none of the three options below add a new competing control for anything AutoBackupCard already owns.
cross-platform check apps/web-react/src/features/backup/{BackupPage,AutoBackupCard}.tsx read for comparison. Web is structurally the same 3-card screen, but it's missing several things mobile already has (added on mobile only, real-device-testing-driven, dated 2026-08-18/21): the foreign_blob banner + its "Overwrite Drive" escape hatch, the navigation lock + "don't close the app" banner while a restore is in flight, and the disabled-only-per-reason button states. These are pre-existing platform disagreements, not ones this task introduces. Per apps/web-react being frozen (CLAUDE.md), none of this redesign needs mirroring there — flagging the gap as a documented finding rather than silently leaving it implicit. If any future decision un-freezes web, this doc is the list of what's already drifted.
scope check — core, not just UI The requested auto-backup on/off toggle + 1–14 day frequency control has no backing logic today. packages/core/src/core/sync/decide.ts's dueDaily is a hardcoded 24h (DAY_MS) in backupEngine.ts; backupPrefs.ts only persists which destination is chosen, not a cadence or an on/off flag independent of destination. Every option below assumes this pref surface gets built (a new "auto-push enabled" bool + an interval in days, both read by decideSync) as a follow-up implementation step once a layout is picked — this mockup is UI/UX only, per the task, but flagging so the toggle isn't mistaken for something a copy change alone would ship.

Recommendation
Option C (Drive-first identity hero, embedded in the existing card — not a new stacked card) is the strongest match for the "Cashew-style" ask: it makes the connected account the visual anchor of Drive backup management the way Cashew and most consumer backup UIs do, while staying inside one card so it doesn't add visual weight per "uncluttered first" (§1). Option A (evolve the existing tabs in place) is the safer, cheaper fallback if the team wants to ship the restore-card and progress-state fixes first and defer the Drive-management upgrade — it's a pure superset of what's already there. Option B (destination rows/accordion) is included for comparison but I'd actively steer away from it: the "tap-to-reveal" accordion pattern (§3) exists for rows with several optional actions that don't all need to be visible at once — here there are only 3 mutually-exclusive destinations and the whole point of the screen is comparing their status at a glance, so hiding 2 of 3 behind an extra tap works against "calm, glanceable hierarchy" (§1) and "minimal clicks to anything" for no real benefit over the segmented control already in place.

Why I don't recommend this one (see the Recommendation box up top): with only 3 mutually-exclusive destinations, the accordion adds a tap to see 2 of the 3 statuses that a segmented control already shows all 3 of, glanceably, with zero taps. It also visually competes with the "grouped rows + tap-to-reveal" pattern as used for Accounts (where each row is an independent item with several optional per-item actions) — reusing it for a single-choice destination picker is a pattern/problem mismatch, not a real reuse.
Option C ★ recommended

Drive-first identity hero — embedded in the same card, not a new one

Keeps the segmented control (so switching destination is still zero-tap-to-compare), but when Drive is selected, the connected account becomes a real hero row at the top of the panel — bigger avatar, account email as the primary line, a clear "Connected" pill — the way Cashew anchors its own Drive backup section, rather than a small status line buried under a generic tab. It's still one card (no extra stacking weight). Tap "Drive", then the ⋮ next to the account, then "Restore from file" below.

Cancel/progress design (shared across all 3 options above): mapped to backupManager.ts's real importBackup() seams, not invented steps — phase 1 covers JSON-parse + key-derive + decrypt (fast, and genuinely nothing has touched the database yet, so Cancel is real and honest here); phase 2 is restoreTables()'s single atomic bulk write (the actual destructive, irreversible step) — the moment it starts, the Cancel link disappears and the copy switches to the same "don't close the app" framing the existing navigation-lock banner already uses. No fake numeric ETA anywhere, per the brief. Implementing this for real needs two small additions to importBackup(): a callback/state param it can report "entering phase 2" through, and (separately) plumbing a real AbortController-style bail-out for phase 1 specifically — today the function has no such hook, it's a straight await chain.
Future idea — NOT buildable today

Drive backup history / multiple versions

Explicitly called out as out-of-scope-today per the brief. googleDriveProvider.native.ts is Model B, appDataFolder, and always finds-or-creates one fixed file (DRIVE_BACKUP_FILE_NAME) — there is no "list of backups" today, and designing a UI that implies one (a scrollable list of 20 individually-downloadable/removable snapshots) would misrepresent what the app actually does. FUTURE IDEA — NOT SUPPORTED TODAY
Requires a real storage-model change: multiple timestamped files (or Drive's own file-revision history) instead of one fixed blob.
A real, grounded lead worth investigating (not confirmed) if this is ever prioritized: because pushImpl() always PATCHes the same Drive file id rather than creating a new one each time, Google Drive's own per-file Revisions API may already be retaining some prior versions of that one file server-side — which could mean a "restore an older version" feature is closer to "surface an existing API" than "redesign the storage model." This is unverified — Drive's revision retention for appDataFolder files specifically (count/time limits, whether keepRevisionForever needs setting) hasn't been checked against current API docs, and it would still show version count/size only, never the "20 independently-named backups" framing above. Worth a dedicated spike before promising it, not something to design against yet.
