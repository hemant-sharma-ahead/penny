Option B's real flaw, not a hypothetical one: toggle to B above and look at HDFC Bank, ICICI Salary, Axis Bank, and SBI Savings — all four render the identical blue icon tile. This isn't a mockup shortcut: AccountFormModal.tsx has no colour picker at all — useAccountForm.ts's selectType() always sets color: meta.color, the fixed per-type default. Since most real users have 2+ "Bank" accounts, B genuinely regresses per-account distinguishability versus what ships today, the moment the bank logo itself isn't sourced yet (SBI here has no logo, so its icon tile is the only differentiator — and B gives it none).
Option C avoids that flaw by keying its accent bar + icon tint off accountCardPalette(id, isCashLike) (hashed on the account's id, exactly like today's gradient) rather than off acc.color — so HDFC/ICICI/Axis/SBI stay visually distinct even though they're all "Bank" type and all share the same unset color field.

Recommendation: Option C (flat card + coloured left accent bar). It's the one option that actually resolves the tension this task named up front — AccountsStrip.tsx (Home) already uses a plain bg-surface/token card, while AccountList.tsx (Accounts) uses a heavy full-bleed gradient; today the same accounts look like two different products depending which screen you're on. Option B would fix that by making Accounts match the strip exactly, but at a real cost demonstrated above: it throws away per-account colour identity for any user with more than one account of the same type (the common case), because Account.color is never anything but the type default today. Option C keeps the strong per-account identity signal (still hashed off id, still immune to the "two bank accounts look identical" problem) while giving up the literal full-bleed-gradient treatment that was the direct target of "does not follow the theme" — the card body itself is now indistinguishable from every other bg-surface card in the app, it just keeps one clearly-scoped, intentional accent instead of none.

Where I'd push back if asked to "just tighten the gradient" instead (Option A): A is the safer, cheaper change and legitimately answers "wasted space" and "no transaction count" — but it leaves "does not follow the theme" only partially addressed: the fixed white-on-gradient text is still a special-cased exception living outside the semantic-token system, and it leaves Accounts and the Home strip disagreeing exactly as they do today. If the team wants the smallest possible diff and is fine revisiting theme-consistency later, A is a reasonable interim step — but given the user's own framing ("does not follow the theme"), I'd go straight to C.
Cross-cutting note — automatic bank detection from account name
Not a UI change — a backend proposal for AccountFormModal.tsx/useAccountForm.ts. The "bank icons not used" complaint is really a data-completeness problem: Account.bankId is optional, there's no way to set it except the "Bank (optional)" picker shown only for bank/credit_card types, and most real account names already say the bank in plain text ("HDFC Savings", "SBI Current", "ICICI Salary A/c") — the exact strings suggested as placeholders in AccountFormModal.tsx today. Proposal: at save time in useAccountForm.ts, if the user hasn't explicitly picked a bankId themselves, run the account's name through a case-insensitive substring match against bankPresetLabels.ts's existing preset list (its keys/labels are already the exact vocabulary to match against: "HDFC" → hdfc, "ICICI" → icici, "SBI"/"State Bank" → sbi, "Axis" → axis, "IndusInd" → indusind, "Kotak" → kotak, "HSBC" → hsbc, "Bank of Baroda"/"BoB" → bob, "Yes Bank" → yesbank, "PNB"/"Punjab National" → pnb, "Canara" → canara, "IDFC" → idfcfirst) and set bankId automatically when exactly one preset matches. Never overwrite a bankId the user set explicitly; never guess when the name is ambiguous (e.g. matches two presets, or a generic name like "Savings Account" matches none) — silently leaving it unset is strictly better than a wrong guess. This alone would put real logos under HDFC/ICICI/Axis for most existing accounts with zero user action, and the two-logo gap (SBI/IndusInd, still shown honestly generic above) becomes purely "logo not sourced yet," not "feature doesn't work."

Cross-platform status

apps/web-react's own AccountList.tsx is frozen (2026-07-31) and was never given the gradient-card treatment at all — it's always been a plain IconBadge + name + type-label + balance row, no chevron, no drill-down modal, no transaction count, acc.color + '20' as the only tint (functionally closest to Option B already, minus the accent-bar identity fix). The two platforms already disagree today, same as the finding recorded in accounts-list-v1.html — that's expected and accepted: web is a historical reference only. This redesign is mobile-only; no web-react mirroring is needed or proposed. If C ships, mobile's Accounts screen and Home's AccountsStrip.tsx will share the token-card foundation (bg-surface/border-theme) for the first time, while still differing on purpose — the strip stays icon-only (horizontal, glanceable), the full list gains the accent bar + txn count + actions a dedicated management screen needs.
