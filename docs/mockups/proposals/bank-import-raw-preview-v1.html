Design decisions
  • Placement: below "Continue to review," per your exact spec — reference material, not a blocker.
  • Which columns show: ALL raw columns from the file (not just the 5 mapped ones) — e.g. "Chq/Ref No." above, which nothing maps to. Seeing an unmapped column is itself useful information (confirms nothing important was silently dropped).
  • Mapped-column callouts: a small green "→ Date" / "→ Narration" tag under whichever raw header Penny actually picked for each of the 5 target fields — ties this table directly back to the "Column mapping" card above it, so a wrong guess is obvious at a glance (the tag lands on a column that clearly isn't a date, for example).
  • Row count: first 5 data rows (excluding the header) — enough to sanity-check date format/column meaning without turning this into a full data browser.
  • Horizontal scroll, not wrapping: real bank exports commonly have 6-10+ columns; wrapping would make the table unreadable, so it scrolls sideways instead, same convention as a real spreadsheet.
  • Data source: reuses useBankImport.ts's already-parsed headers/tokenizedRows (currently internal-only) — needs exposing on the hook's return value, not a new parse path.
Open question Should this table appear as soon as a file is picked (even before a bank/mapping is fully resolved), or only once bi.headers.length > 0 (i.e. right where "Column mapping" already gates itself)? I'd default to the same gate as "Column mapping" — it needs the same parsed data, and showing it any earlier would mean showing raw rows with no mapping context to compare them against yet.
