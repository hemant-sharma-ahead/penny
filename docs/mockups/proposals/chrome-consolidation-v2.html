Global chrome consolidation v2 — Home vs. other tabs

Redo of chrome-consolidation-v1.html, which was rejected: all 3 options were placement variants of one idea ("a slim bar with a single ⋮ icon"), and it never actually rendered today's real screen for comparison. This version starts with two accurate current-state frames, then proposes 4 structurally different interaction concepts — different mental models, not reskins of the same bar.

Ground truth re-read for this pass: MainTabs.tsx (persistent header + tab navigator mount point) · ContextSwitcher.tsx · PrivacyModeSwitcher.tsx · RemindersBell.tsx · HomePage.tsx / GlanceHeader.tsx · PortfolioPage.tsx (has its own PageHeader already) · GoalsPage.tsx / ExpensesHeader.tsx (also have their own PageHeader) · ChipPage.tsx (does not have a PageHeader today — relies entirely on MainTabs' chrome, a real gap called out below) · docs/DESIGN_GUIDELINES.md (updated 2026-07-31) · header-options.html / home-v2.html / chrome-consolidation-v1.html for reconciliation.

What v1 got wrong, specifically: it read the source correctly but never built an HTML frame that actually looked like today's app — so there was nothing to compare the 3 new options against. Every section below places a proposed concept directly next to the two "Today" frames. It also proposed only one shape (icon bar, blank/wordmark/title on the left) three times; this pass treats "a top bar" itself as one option among several, not a given.

Concept A

Ambient colour only, zero top-chrome icons — long-press the tab bar for actions

Deletes the header row entirely on every tab. All that's left up top is a 3px colour strip tinted by privacy mode — literally the same amber border that already exists today, just promoted to be the entire remaining top chrome once the row above it is gone. Settings / Reminders / Privacy-mode switching move to a long-press on any bottom tab icon (the one element already persistent and thumb-reachable on every screen) — the same centred menu opens regardless of which tab you held. Home's "Personal ▾" context pill folds inline into the greeting text itself (page content, not chrome).

Tradeoff: maximum decluttering (reclaims the full 44px header + the ContextSwitcher bar's height on every non-Home tab), but long-press has no visual affordance — DESIGN_GUIDELINES's "reuse patterns the user already knows" cuts against this: RN tab bars don't have a standing long-press-for-menu convention the way, say, iOS home-screen icons do (and that's a different context — jiggle mode, not a menu). Would need a one-time coach-mark on first run, and it's genuinely unclear whether a 3px line still satisfies DESIGN_GUIDELINES §2's "header + nav always visible" or reads as having removed the header.

Concept B

Pull-down quick-actions shade — the OS notification-shade gesture

Borrows the one gesture every phone owner already knows: swipe down from the top of any screen to reveal a drawer of quick actions; swipe up or tap outside to dismiss. The one persistent hint — identical on every tab, so it never looks "populated on Home, empty elsewhere" the way v1's rejected options did — is a small centred handle pill just under the status bar. Pulled open, the drawer shows a one-tap privacy-mode segmented row (still centred, still PIN-gates Open mode via its own follow-up modal), a 2-line Reminders preview, and a Settings row.

Tradeoff: the gesture itself is maximally familiar (satisfies "reuse patterns the user already knows" better than any other concept here), but it's a brand-new interaction language for Penny specifically — nothing in the app today responds to a swipe-from-top. Real build cost (gesture-handler, conflicts with any future pull-to-refresh on Home/Portfolio). And structurally this is an edge-anchored overlay, not a centred one — DESIGN_GUIDELINES's "no bottom sheets" rule doesn't literally cover a *top* sheet, but it's the same shape-class the rule exists to avoid; worth an explicit sign-off rather than assuming it's fine by the letter of the rule.

Concept C

Greeting-card avatar as command centre — no new global chrome at all

Instead of adding anything, this deletes MainTabs' persistent header + the always-mounted ContextSwitcher outright — a real structural simplification, not just a visual one, since Portfolio/Goals/Expenses already render their own PageHeader today (MainTabs was stacking a redundant second header above it). One small circular avatar chip — initials, ringed in the privacy-mode colour as a passive signal — gets added to the trailing side of whatever header each screen already has: Portfolio/Goals/Expenses' existing PageHeader, and Home's own greeting row. Tap it anywhere → the same centred command menu.

Tradeoff: cheapest to build (deletes a layer instead of adding one) and keeps the letter of "header + nav always visible" fully intact — but two real gaps: (1) Chip's screen has no PageHeader today, so this concept requires giving it one first, a small but real dependency; (2) Home's greeting row scrolls away with the rest of the page today (unlike the other tabs' pinned PageHeader) — so on Home specifically, the one access point to Settings/Privacy/Reminders would become unreachable once the user scrolls past the first screenful, a real regression from today where the header is always pinned. Would need Home's greeting row to become sticky, which it isn't today.

Concept D · recommended

Persistent floating avatar bubble — one universal element, pinned everywhere

A single small circular button, pinned to the same top-right corner on every tab including Home, overlapping the top edge of whatever content is underneath (the same "always-on-top bubble" pattern a video-call app uses for a self-view). Ring-tinted by privacy mode; shows initials by default and a small red dot when reminders are due. Because it's pinned rather than living inside any card or header row, it stays reachable at any scroll position, on every tab, identically — solving both v1's "empty header on 4 of 5 tabs" inconsistency and Concept C's "scrolls away on Home" regression in the same move. Tap it → the same centred command menu as every other concept here.

Tradeoff: it's the one genuinely new visual language in this whole set — nothing in Penny floats over content today, so it needs its own entry in DESIGN_GUIDELINES's z-index ladder (above page content, below modals) and a documented collision rule for any screen that already places its own action in that corner. That collision is real and visible below: Portfolio's "Refresh prices" pill already lives top-right of its own header — the bubble needs to sit clearly above/beside it, not on top of it.

Findings & recommendation

What today's chrome actually costs (verified in MainTabs.tsx): every non-Home tab pays for a 44px header + (when the sync entitlement is on) a further ContextSwitcher bar, on top of its own PageHeader that Portfolio/Goals/Expenses already render — two stacked headers doing overlapping jobs. Chip is the one tab with no PageHeader of its own at all, so it's currently the most dependent on MainTabs' chrome surviving in some form.

ConceptMental modelBiggest strengthBiggest risk
A — Ambient colour + long-press tab barNothing to look at; everything felt via colour + a hidden gestureMaximum decluttering; reuses the accent border that already existsLong-press has no discoverability — violates "reuse known patterns" without a coach-mark
B — Pull-down shadeOS notification-shade gesture, borrowed wholesaleMost familiar gesture of any concept hereBrand-new interaction language for this app specifically; an edge-anchored sheet in spirit, if not letter, of "no bottom sheets"
C — Greeting-card avatarNo new chrome; consolidate into what each screen already hasCheapest to build; literally deletes a redundant layerHome's entry point scrolls away (regression); Chip has no header to attach to yet
D — Floating avatar bubbleOne pinned, universal element, identical on every tab and scroll positionSolves both A/B's discoverability problem and C's persistence problem at onceThe one genuinely novel visual pattern; needs a documented z-index rule and a collision fix on Portfolio
Recommendation: D, built on top of C's structural insight. Delete MainTabs' persistent header and always-mounted ContextSwitcher outright (that redundant layer should go regardless of which concept ships) and replace the single global mount point with the floating avatar bubble, pinned per-screen. It's the only concept that satisfies DESIGN_GUIDELINES's "spatial stability builds trust" in the way that principle is actually meant — reachable identically from anywhere, not just at the top of a scroll — while still being a real, one-tap-away entry point (satisfies "minimal clicks") and passively signalling privacy mode through its ring colour without a dedicated icon (satisfies "privacy is the product, not a feature"). B is the runner-up on pure familiarity grounds but carries real build risk this doesn't; A is rejected outright for the same reason v1 was — invisible affordances aren't "uncluttered," they're just hidden.
Open for you to weigh in on:
  • Sign off on the floating-bubble visual language itself — it's new for Penny; if that novelty is unwanted, Concept C (with Home's greeting row made sticky, closing its one real gap) is the safer fallback and should be said explicitly rather than defaulted into.
  • How to resolve the Portfolio top-right collision between the bubble and the existing "Refresh prices" pill (options: bubble sits a half-row higher overlapping the status bar; Refresh prices moves inline with the Holdings/IPO tab row instead).
  • Badge treatment on the bubble when reminders are due — a plain dot (shown here) vs. a numbered badge like today's bell.
  • Chip's screen has no header today under any of these 4 concepts except D (which doesn't need one) — confirm D avoids that dependency, or if C is picked instead, Chip needs a minimal header added first.
  • Exact command-menu row order (Privacy → Reminders → Settings shown here, matching today's left-to-right header order) and whether Home's inline "Personal ▾" pill should also be reachable from the bubble's menu for consistency, even though functionally it's only ever needed on Home.
