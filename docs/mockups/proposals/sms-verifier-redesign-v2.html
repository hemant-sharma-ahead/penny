3Capture-group highlighting — everywhere, always onconfirmed
Promoted from "bonus idea" to a core, always-on part of the tool per feedback: color-coded highlighting of exactly what each field captured, directly on the raw SMS text — not just in Section 1's browse cards, but in Section 2's expanded table rows too (already shown there), and for every template/message, not a one-off illustration. Same color per field everywhere it appears (green=amount, blue=account/card, pink=counterparty, etc.) so the mapping is learned once and stays consistent.
Cheap and already threaded through: traceSms()'s per-attempt regex .exec() result has named-group start/end indices available for every match, in both Section 1 (browsing) and Section 2 (testing) — wrapping the matched substrings in <mark> tags is a small shared rendering helper (.smstext in the CSS), no new parsing logic, one implementation used by both views. Only applies where a template actually matched — an unmatched attempt has nothing captured to highlight, which itself is informative (you can see nothing lit up).
Other small ideas, lower priority — happy to fold any of these in too:
• When a sender is completely unrecognized, a soft "closest known sender ID" suggestion (fuzzy match against configured senderIdPatterns) — helps distinguish "this bank isn't configured at all" from "this bank IS configured but the sender ID variant is slightly different than expected."
• A "download this session's results as JSON/CSV" button (in addition to the existing redacted-copy-as- text) — matters more now that testing scales to thousands of messages (Section 2), so a real export format is worth having alongside plain-text copy.
4Add a parser — design and verify a new candidate, livenew
A third mode alongside Known templates / Test your own — reachable three ways: this standalone mode (for a bank that isn't configured at all yet), the dashed "+ Add a template" card at the bottom of a bank's template list (Section 1), or the "+ Add a template, pre-filled from this message" action on an expanded partial-match row (Section 2). All three open the same form. Draft a template, test it immediately against pasted samples, and — once it works — it's automatically included in every other view for the rest of the session (Known templates, Test your own) and exportable as ready-to-paste code for a developer to actually add to smsPatterns.ts.
Kept session-only + explicit-export by design, never auto-writes to any file — this is a verification tool, not a code generator that silently changes the real pattern library. A developer still deliberately pastes the exported snippet into smsPatterns.ts and reruns pnpm build:sms-verifier for it to become real, shipped config.

My take: all four sections are worth building together now — they're not independent features, they reinforce each other. The match trace (②) is what makes a gap visible; the "+ Add a template" actions reachable directly from that gap (Section 1's dashed card, Section 2's expanded-row action, both opening Section 4's form) are what make it fixable in the same sitting; the highlighting (③) is what makes a new regex easy to verify while drafting it. The table+tabs rework of Section 2 isn't optional either once real testers start pasting hundreds/thousands of messages — the old full-card view would make the tool unusable at that scale, not just less polished. The two remaining "other small ideas" (fuzzy sender suggestion, JSON/CSV export) are genuinely lower priority — fine to defer.

Summary of what changes

  • Core module (real code change): new traceSms() in packages/core/src/core/sms-import/smsParser.ts, returning every template attempt for the sender-matched bank (matched or not), plus each match's capture positions (for highlighting). parseSms() becomes a thin wrapper deriving its existing return value from it — one copy of the matching logic, existing tests unaffected.
  • Browse view (Section 1): a sender-patterns box above the template cards; each card gets a "copy regex" button and highlighted capture text; a dashed "+ Add a template for this bank" card at the end of every bank's template list.
  • Test-your-own view (Section 2), reworked for scale: filter tabs by outcome (Parsed / Partial / Unrecognized / Excluded, each with a live count), a dense one-line-per-message table instead of full-width cards, click-to-expand for the full trace + highlighted text, a file-upload option alongside pasting for testing a whole exported message history at once, and a direct "+ Add a template, pre-filled from this message" action on any expanded partial-match row.
  • Capture-group highlighting (Section 3): always on, shared between the browse and test views (one .smstext rendering helper, not two implementations) — no longer a "bonus," a core part of both.
  • Add a parser (Section 4): one form, three entry points (its own mode, or contextually from Sections 1/2). Validates regex live, tests against pasted samples immediately, then either "Add to this session" (folds into the in-memory bundle every other view uses, marked draft) or "Copy as code" (ready-to-paste SmsTemplateEntry). Session-only, never auto-writes to any file — a developer still deliberately pastes it into smsPatterns.ts and reruns pnpm build:sms-verifier for it to become real, shipped config.
