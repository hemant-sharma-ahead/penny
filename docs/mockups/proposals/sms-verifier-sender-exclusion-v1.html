Sender & Message Exclusion — proposal v1

The core idea: split "Unparsed" into two genuinely different things — a real coverage gap (recognized bank, wrong wording, worth a new template) vs. not a transaction at all (OTP, promotional, government, non-financial service pings). Auto-detect what's cheaply detectable (OTP keywords, the TRAI −P/−G suffix); let you manually exclude a whole sender or just one message for everything else. Both sections below are clickable — try excluding a sender, clicking a sender name to filter, or undoing an auto-exclusion.

2 Real app — Unparsed Messages screen

Same underlying idea, ported to the already-shipped sender-grouped accordion screen: each group's header gains an "Exclude sender" action next to the existing "Dismiss all" — durable and persisted (a new sms_excluded_senders table), so this sender never creates a fresh "unparsed" record again on a future scan or live capture, not just a one-time dismiss of today's batch. A collapsible "Excluded senders" strip at the top lets you undo one if you change your mind. Per-message "Not a transaction" stays available inside a still-included sender's own messages, for senders that mix real transactions with noise.

Open questions to confirm before implementing:
• New Dexie table sms_excluded_senders (id, sender, createdAt) — checked by processRawSmsCore before creating an 'unparsed' record (treated like an unrecognized sender: dropped, never persisted) — applies uniformly to historical scan, foreground live capture, and the Headless JS background path, since all three funnel through the same function.
• Auto-exclusion (−P/−G suffix) is a display-time classification only in the tool (no schema change there); in the real app it would need the same "auto, but undoable" treatment — worth deciding whether the real app auto-excludes on first sight or only suggests it, independently of the tool's already-confirmed answer.
• Undoing an exclusion (tool or real app) never retroactively restores anything that was already silently dropped before the rule existed — it only stops applying going forward, same non-destructive spirit as every other session/settings toggle in this project.
