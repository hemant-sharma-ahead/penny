A — Bucket sections

+ Familiar — literally reuses bank-import's own accordion taxonomy, zero new pattern to learn.

− Applies one uniform interaction (collapsed, tap-to-open) regardless of urgency — the single real conflict gets exactly as much default visibility as "9 things that need no decision at all." Risks the one row that matters going unseen, which is the specific failure doc §6.5 calls out.

B — FY-native list

+ Continuous with the list the user already sees on this exact screen (EpfAllTransactionsSheet's own month rows) — no new mental model.

− The one conflict sits chronologically sandwiched between "Matches" rows above and "New" rows below — easy to scroll past mid-list on a 13-row screen, worse on a bigger multi-employer batch.

C — Conflict-first triage

+ Structure = priority: act → skim → ignore, top to bottom. Directly implements doc §6.5's own explicit asks almost verbatim (distinguish states, quiet-summarize matches).

− Trades chronological order for priority order — a minor cost given this is a one-time review screen, not a recurring browse view.

Recommendation: Direction C

Go with C — conflict-first triage. The plan doc is explicit that the conflict case should be "the clearest, most carefully designed state," and that matches should collapse into a quiet aggregate rather than being listed row-by-row — C is the only one of the three that satisfies both asks structurally, not just cosmetically. A and B both treat all three outcome types as equally-weighted list content and rely on the user to notice the one that's different; C makes noticing it structurally unavoidable. The chronological-order loss (B's advantage) doesn't cost much here — this is a one-time confirm-before-write screen, not a recurring transaction browse, so "what happened when" matters far less than "what do I need to do." One addition worth keeping from bank-import's own pattern: the New section's checkboxes (pre-checked, individually toggleable) — shown in C above — so a user who spots a row they don't actually want imported can drop it without aborting the whole batch, consistent with bank-import's UnmatchedBucket doing the same thing for its own list.

Cross-platform note

EPF passbook import is a brand-new capability with no prior implementation on either platform, so there's no existing disagreement to flag — apps/web-react's RetirementSheets.tsx/RetirementCard.tsx are currently at parity with mobile's (same "+ Add" ghost button, same PPF banner pattern, same modal structure). Per this repo's default rule, a genuinely new capability would normally get mirrored on both platforms — but apps/web-react is explicitly frozen as of 2026-07-31 ("no further changes"), so unless told otherwise, this proposal is scoped to apps/mobile only, matching the actual task and this file naming. Flagging this explicitly rather than silently deciding it either way, per this repo's own "call out whether it needs mirroring" rule.
