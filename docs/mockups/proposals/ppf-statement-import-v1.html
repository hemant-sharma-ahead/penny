PPF statement import — UI proposal (v1) docs/features/portfolio/retirement.md · grounded in the real current PPF card (RetirementCard.tsx), PpfModal.tsx/PpfFields.tsx, and EPF's already-approved reconciliation review pattern (epf-passbook-import-v4.html)

Same feature as bank Statement Import (CSV/Excel upload → bulk-populate), scoped to PPF: launched from the PPF card, committed as real PpfTransaction rows (deposit/interest/withdrawal), not generic bank transactions. Reconciliation follows EPF's exact-key model (new/matches/conflict), not bank-import's fuzzy 4-bucket matcher — a PPF statement is low-volume and structured, the same reasoning that made EPF diverge from bank-import. New this round: since a bank PPF statement always includes the annual interest row, the review screen shows a fresh recalculation next to it (using the new PPF rate table) so a wrong/estimated recorded figure is caught at import time, the same sanity-check EPF's import already does.

Recommendation

Reuse EPF's approved review layout as-is (it's already validated, and PPF's data is a strict subset — flatter, lower-volume). The one genuinely new element is the calculation card for interest rows: always shown when a rate table is available, three states — Matches (quiet, reassuring), Differs (flagged, but the statement's own figure stays the kept default — never auto-corrected, since it's what was actually credited), and Not verified (when Penny's own record doesn't go back far enough to trust the recalculation — shown for transparency, explicitly excluded from the match/differ judgment rather than silently treated as a match or conflict it isn't).

3Missing-details gate
A bank statement never contains opening date/bank/name — the fields §0.3's "Track PPF" form collects. Rather than a separate modal push (which would feel like a detour), this renders as one more step inline in the same flow, directly after Import is tapped, reusing the same field components.
Inline step, before commit recommended
Shown once, right after reconciliation, before "Import N transactions" finalizes — for either a brand-new PPF holding created by the import, or an existing one missing a field it was allowed to skip (bank is optional today). Opening date is pre-filled from the earliest imported row as a starting SUGGESTION, not silently assumed — the real account may predate the statement.

Implementation notes (not visual — for the build step)

Core logic (all built already, this round's mockup is UI-only): ppfStatementParser.ts (reuses bank-import's grid/date primitives directly, adds classifyPpfRow), ppfReconciliation.ts (exact-key new/matches/conflict, wires in calculatedInterest per interest row), ppfInterestCalculator.ts (the real 5th-of-month accrual rule — different from EPF's own accrual timing, do not copy EPF's rule here).

Still open for the build step: whether the "Track PPF" holding-creation path (untracked CTA → import) needs its own lightweight file-picker entry before the missing-details step, mirroring RetirementUntrackedCard's existing epfImportFiles state pattern — should be a direct copy of that existing code path, not a new design.
