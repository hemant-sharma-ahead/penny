Recommendation: ship the starred option in each section.
  • §1 — Stacked icon, one row. This is your own fix, and it's the right one: it's the only option that gets a real one-row-of-numbers layout without sacrificing name legibility or resorting to the tightest type on the card. Bank-specific icons are a real idea worth doing eventually, but they need a new asset system first — don't block this layout fix on that.
  • §2 — Redesigned (Accounts + Transactions only). This is the one that actually answers "why do people fall back to some apps again and again" (DESIGN_GUIDELINES.md §1) — a clean file should feel like 2–3 taps total, not a forced tour of 5 screens plus a 2-modal dance for every account that needs mapping. The counterparty-chip fix isn't a cosmetic patch on top of the explosion bug — it's a structural side effect of removing the stage that caused it, which is exactly the kind of fix docs/DESIGN_GUIDELINES.md's "one capability, one control" principle argues for over patching each exploded row individually.
  • §3 — Persistent scrub bar. "Last month" and "this month" are the overwhelming majority of real taps, and those should never cost a modal. The flat list is a reasonable fallback if the scrub bar's always-visible row turns out to be a bigger screen-space cost than expected once seen against the real, already-busy filter bar.

Judgment calls & open questions for review

  1. §1 — abbreviation length under the icon. Used a 4–6 character truncation ("HDFC", "Cash") in the 54px stacked column. A real implementation needs a rule for what to show when even that overflows (e.g. "ICICI Bank" → "ICICI"?, or a user-set 2–3 letter initials field) — not fully specified here, flagging as a real decision the ported component will need to make.
  2. §1 — decimal-fit demonstration. Same reasoning as v1: formatCompact only shows decimals below ₹1,000 (checked packages/core/src/lib/formatters.ts), so the real fit risk is specifically a low-activity account (Cash) — used the same HDFC/Cash pair on purpose so both the compact-notation case and the decimal-fit case are visible together.
  3. §2 — account-resolution tap counting. Modeled the smart-match "wrong guess" path as 2 taps ("Not this account?" + picking the correct alternate pill) and the "kind isn't Existing" path as 1 tap (the segmented pill itself resolves it, no second step) — both real, different paths through the same control, not two separate features. The exact tap count for a genuinely ambiguous multi-way merge (not modeled here) would likely still need 2, same as today's "wrong guess" case.
  4. §2 — counterparty-chip tile is a representative sample, not the full 16 rows. The "after" state shows ~5 real per-row chips plus a "…and 11 more" note rather than rendering all 16 inline, on the theory that a real `TileRowList` already has its own render cap (`docs/ARCHITECTURE.md`'s 2026-08-13 entry) — this mockup doesn't re-litigate that cap, just demonstrates the chip itself.
  5. §2 — where the confidence indicator's exact wording/thresholds land. Used "Auto-matched" (green, collapsed, no tap) vs. "Needs confirming" (existing needsConfirming badge language from `CategoryTile.tsx`) rather than a numeric confidence percentage, since no percentage-based UI exists anywhere else in the app today — flagging as a deliberate choice to reuse existing vocabulary, not an invented new one.
  6. §3 — scrub bar's visible window size, corrected. At the real 390px frame, 6 chips fit comfortably (v1's undersized 280px frame under-counted this at 5) — still a mockup approximation; the real implementation should size to the actual device width rather than a fixed count.
