Recommendation: ship all five as designed here — each reuses an existing Penny pattern rather than inventing one, which is exactly the bar DESIGN_GUIDELINES.md §1 sets ("reuse patterns the user already knows"). The one place worth a deliberate second look before implementing is §3 (delete/archive) — it intentionally converges two currently-independent silent delete paths (PersonForm's Remove and IouView's Archived-trash) onto one popup + one non-cascading delete function, per the "duplicated capability" rule. That's a slightly bigger change than "add a dialog," but doing it piecemeal (a toast on one path, a check on the other) is the exact mistake already made once on Backup & Restore — worth avoiding a repeat.
  • Cross-platform: checked apps/web-react's ExpenseForm.tsx, FilterModal.tsx, and features/iou/* for all five items — every gap exists identically on web too (no edit-mode toggle, no Tag filter section, no delete confirmation, a plain field instead of a type-ahead for Lent/Borrowed). Since apps/web-react is frozen per CLAUDE.md, none of this proposes touching it — flagging only because the task asks whether the platforms already agree or disagree, and here they agree (both lack it).

Judgment calls & open questions for review

  1. §1 blocked-state copy — used a Banner variant="info" below the disabled SegmentedControl, mirroring this exact file's existing audit-trail/payment-mode-mismatch banners. The plan doc also floats a "tap-to-explain toast" as an alternative; a persistent Banner reads better here since the reason is a standing fact about the transaction, not a one-off event — but it's the more visible of the two options, worth confirming.
  2. §1 "category cleared" caption — added a small tertiary caption under the tile ("Category cleared — pick one for Income") on top of the tile's own pre-existing empty-state look. Not explicitly requested; the dashed-border + "Select category" state might already be legible enough on its own. Easy to drop if it reads as noise.
  3. §3 popup component — built as a custom centered Modal, not the literal ConfirmDialog, because this needs two non-cancel choices (Archive / Delete) rather than ConfirmDialog's strict Cancel/Confirm contract. The outstanding-balance variant's "Delete permanently anyway" is a de-emphasized text link rather than a real button, then routes into ConfirmDialog for a real second tap — a "strong warning" reading of the plan doc's "block (or at minimum a strong warning)," not a hard block. Flag if a hard block (no permanent-delete path at all while balance ≠ 0) is actually wanted instead.
  4. §4 bulk action label — used "Person" to match the existing bar's brevity (Category/ Account·Pay/Hashtag/Delete are all one word). "Add to person" from the plan doc's own phrasing doesn't fit the same visual rhythm at that width.
  5. §4 step count — modeled as up to 3 steps (person, expense-direction, income-direction) plus a non-counted final summary/apply screen. If a selection is single-direction only, it collapses to 2 real steps + summary, matching "2–3 steps" from the plan doc.
  6. §5 tag chip icon — no color field exists on Hashtag (checked packages/core/src/core/db/types/index.ts), so tag chips use a plain ti-hash icon per chip rather than a per-tag dot color the way Account/Category tiles get one from their own domain color.
