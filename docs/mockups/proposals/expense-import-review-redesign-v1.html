9"Select all" no longer a footgun — Issue #9
In a tile with more than 8 rows, today's "Select all" only ever selects the visible 8, silently leaving the rest of the group untouched. Fix: selection is tracked as a Set<number> over the tile's full logical row-index set, entirely decoupled from what's currently rendered. The master toggle ("Select all" / "Unselect all") always means literally every row in the tile — whether or not it's on screen — with no separate "load all first" step required. The "N of M rows shown" cap becomes a pure display/performance concern, with its own unrelated "Show all" affordance for anyone who actually wants to scroll and look.

Recommendation: ship all ten together as one pass — they all touch the same PreviewSection/CategoryTile/useImport surface, and several are genuinely coupled (the moved-row fix and the transfer-homogeneity fix both need the same "tiles are live-recomputed off each row's real destination" groundwork; the checkbox-contrast fix and the default-checked fix touch the exact same JSX). Splitting them into separate PRs would mean re-deriving that shared groundwork twice. The one piece I'd genuinely stage separately is the Ready/Needs-input grouping (#6) — it's the least load-bearing (pure section labels over an ordering the code already computes) and easiest to drop if it reads as visual clutter once it's in front of real data.
Open questions / judgment calls I made — flagging for your decision:
  1. Attention gate's "Skip for now" (#7): I modeled this as excluding those rows from the batch entirely (same as the existing per-source "Skip" kind) rather than importing them under a generic fallback category. If you'd rather they land in a catch-all "Uncategorized" than be dropped, that's a one-line change to which existing CategoryAction kind it maps to.
  2. Un-pairing a transfer (#4) mid-review: after "log separately", I show the two legs immediately as their own attention tiles (needing a fresh category decision each) rather than trying to guess one. Guessing felt riskier than an honest "needs your input" — but it does mean un-pairing always creates at least one new decision to make.
  3. "Remembered" pill (#8): this mockup only specifies the surface, not the matching rule (e.g. exact-normalized-description match vs. fuzzy). Bank Import's merchantMemory.ts already solves a very similar problem — worth checking whether Expense Import can reuse that logic directly, or whether its rows (no merchant-narration concept, just a free-text categoryName) need a different matching key. That's an implementation question, not a design one, but it'll affect scope.
  4. Readiness grouping (#6) and homogeneity (#10) interaction: once a tile is guaranteed single-type, a source category that's genuinely mixed (some rows expense, some income, no transfer relationship at all — e.g. a shared "Reimbursement" label) now always produces two tiles instead of one. I think that's correct (it's exactly the bug #10 describes), but it does mean the tile count for a messy real-world file could go up, not down, after this redesign — worth knowing going in.

Where each fix actually lives (implementation-facing, for when this is approved)

  • #1 default-checked — CategoryTile.tsx's selected state initializer (currently new Set()) seeds every row's index instead, matching UnmatchedBucket.tsx's own "everything checked, track the exceptions" convention.
  • #2 checkbox contrast — a shared style, not a copy-pasted one: worth pulling the checkbox visual into a tiny shared piece (or at minimum shared token values) so CategoryTile.tsx and Bank Import's own inline checkboxes stay in sync going forward, per "keep shared controls in sync."
  • #4/#10 transfer + homogeneity — needs PreviewSection.tsx's rowsByCategory grouping to exclude any row already claimed by transferPairs, and to split by row.type within a source-category key, not just by sourceName alone.
  • #5 moved row — effectiveTileKey() already computes the right destination key; the gap is that it doesn't yet create a fresh tile identity for a destination category with no existing source-name tile of its own (today it only regroups into an already-existing tile via tileForExistingCategoryId).
  • #7 attention gate — ReviewStep.tsx's Import disabled condition needs one more clause alongside !accountsResolved || !transfersResolved: no tile left in an unconfirmed "create" state that hasn't been explicitly acknowledged or skipped.
  • Group tagging is unchanged — the "Tag all transactions" / "Tag N selected" pill in every tile's pillrow is not being removed or altered by this redesign. A tile that loses row(s) to the new "Already imported" bucket (#3) keeps its own tag control exactly as before, just scoped to whatever rows remain in that tile.
