Mark as paid — correct per-installment amounts when a discount is active

The exact scenario from the brief: ₹12,000 annual premium, 10% first-year discount, Monthly frequency. Year 1 should show ~₹900/month, Year 2 onward ~₹1,000/month — not one flat annual number. Try it live in §②'s interactive form above (Monthly + 10% discount is already the default) — the worked example below is a static, easy-to-verify reference for the same numbers.

Worked example — Term, ₹12,000/yr, 10% first-year discount, Monthly
Full (undiscounted) installment₹12,000 ÷ 12₹1,000/mo
Year 1 installment (10% off)₹10,800 ÷ 12₹900/mo
01 Apr 2026 — Installment 1Year 1₹900 ✓ paid
01 May 2026 — Installment 2Year 1₹900 ✓ paid
01 Jun 2026 — Installment 3Year 1₹900 ✓ paid
… (9 more Year-1 installments at ₹900) …
— Year 2 begins —
01 Apr 2027 — Installment 13Year 2₹1,000
01 May 2027 — Installment 14Year 2₹1,000

Penny computes which figure applies automatically from the discount + frequency + how many installments have already been marked paid — the user never does this arithmetic themselves, and never sees a wrong "₹1,000" charged in month 1 or a wrong "₹900" charged in month 13.

micro-interaction Tapping "Mark as paid" in §②: (1) records the current installment at today's computed amount, (2) shows a brief green confirmation line ("✓ Marked ₹900 paid for 30 Sep 2026. Next due: 31 Oct 2026."), (3) rolls "Next premium due" forward by exactly one frequency interval, and (4) prepends a new row to the Payment history list with a ~1.5s highlight flash that settles into a normal row. The list shows the 3 most recent entries by default with a "Show N more" link — capped so a 10-year Monthly Limited-Pay policy (120 rows) never renders unbounded, consistent with this project's "any list of bulk/repeating data needs a render cap" rule.

Exactly what's reused vs new
  • Reused as-is: the bell + badge, the centered Modal, the Overdue/Due today/Coming up grouping and ordering, the IconBadge + label + due-label + amount row shape, the Snooze/Done buttons, the ti-shield / #10b981 insurance icon+color already defined in cashflow/meta.ts.
  • New: the label reads "{insurer} {type} — Premium due" instead of "{insurer} renewal" (still generated the same way, just a different string), a "mark_paid" action value, and the amber grace-period caption row on an overdue-but-in-grace item (new, but reuses this section's own row shell — no new component).
implementation dependency Today, forecaster.ts's insurance block emits exactly one flat annual event per policy (ins-${'{'}p.id{'}'}, ${'{'}p.insurer{'}'} renewal, p.annualPremium, from p.renewalDate). Making these 3 scenarios real needs: (1) the insurance block to emit one event per actual payment-frequency occurrence within the forecast horizon for Term/Life, sourced from §②/§③'s new nextPremiumDue + frequency fields instead of one flat renewalDate; (2) using the §④ discounted per-installment amount for whichever occurrences fall inside the first-year window; and (3) buildReminders() gaining a new action: 'mark_paid' value and RemindersBell.tsx gaining one new button branch (mirroring the existing 'log' branch). Flagging this as the real dependency this design has on the forecast engine — not solving it here.
⑧ For you to weigh in on

Design decisions made, and open questions

Decided in v1 / v2 (unchanged)

  • Nominee(s) is Term/Life-only. "Premium payment term" (Regular/Limited pay) is Term/Life-only, hidden for Single premium. First-year discount is a one-time year-1 modifier, never a permanent override. Duration presets and insurer lists are type-scoped. Vehicle insurance fields stay unlinked from Real Assets' own Vehicle-holding fields. Switching type silently resets the insurer. Age-based duration chips read the saved profile DOB locally. A custom "Other" insurer is remembered as a local suggestion, reusing the app's existing "Frequent" chip + PersonTypeahead patterns.

Decided this round (v3)

  • decidedULIP toggle. A simple boolean on the Life type's fields ("Market-linked (ULIP)?"), used purely to pick 3-year vs. 5-year revival-window copy — not a full type split (Term/Health/etc. still don't need it), not a generic imprecise range.
  • decided"Mark as paid" + per-installment discount math. The "Annual premium" field is the one number the user enters (matches the real annualPremium schema field); frequency and an active first-year discount both purely affect how that figure is displayed/split per installment, never re-interpreted as a different entered value. §④'s worked example (₹12,000/yr, 10% off, Monthly → ₹900/mo Year 1, ₹1,000/mo Year 2+) is the reference case.
  • decidedReminders integration reuses RemindersBell.tsx exactly — no new banner/notification component. Term/Life premium-due reminders become another row using the exact same shell as today's recurring-bill/EMI/subscription reminders, with a new "Mark as paid" action parallel to "Log it".

Open questions

  • confirmShould "Mark as paid" ever create a real ledger Expense entry (so the payment shows up in Transactions/Cash Flow like any other spend), or stay purely a due-date-tracking action with no ledger effect? Explicitly deferred per your instruction not to over-engineer the data model this round, but it's the natural next question once this ships.
  • confirmReal Indian insurers commonly apply a small "modal loading" surcharge for non-annual frequencies — WebSearch confirms paying monthly typically costs roughly 3–5% more per year than a plain annual-premium-÷-12 split (annual mode avoids this and may even get its own small discount). This mockup's per-installment math is a clean divide-by-N with no loading, which is simpler but not fully how real insurers price it. Acceptable simplification for v1 of this feature, or should an optional "modal loading %" field be added alongside the existing first-year discount?
  • confirmOnce §⑦'s forecaster change ships, a monthly-pay Term policy generates up to 12 reminder occurrences a year versus one annual event today for every other insurance type — is that a concern for reminder-list noise/volume, or fine as-is since Snooze/Done already exist for exactly this?
  • confirm(carried over, still open) Health's co-pay stays a single flat %; some real policies have tiered/room-rent-linked co-pay that doesn't reduce to one number — still fine to leave that nuance to the free-text Notes field?
