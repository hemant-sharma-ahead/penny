PPF manual-entry FY-order guard — proposal, v1

A safeguard for PpfTransactionSheet (add/edit deposit·interest·withdrawal) mirroring the class of bug just fixed in ppfReconciliation.ts: a later year's interest — or even just a later deposit — can no longer be entered before an earlier year's own interest is actually recorded. Built on top of the already-correct, already-tested findMissingPpfInterestFys / computePpfInterestOnDemand — this is UI wiring, not new calculation logic.
Scope: apps/mobile only. apps/web-react's RetirementSheets.tsx has the same PpfTransactionSheet shape today, but per CLAUDE.md web-react is frozen (no feature work) — no mirroring proposed there. CSV import (ppfReconciliation.ts) is explicitly out of scope — it already handles the multi-year case correctly since the recent fix.

1Gap-guard warning — blocked Save
missingFys = findMissingPpfInterestFys(...) → earliestMissingFy. Any transaction (deposit, withdrawal, or interest) dated in a FY after the earliest missing one is blocked — a transaction dated within/before the gap year itself is untouched (you can keep depositing into FY2023-24 right up to its own year-end; that's normal).
Example shown below: FY2023-24's interest was never recorded. The user opens "+ Add" and tries to log a routine deposit dated 15 Aug 2025 (FY2025-26 — two years past the gap). Save is disabled; the banner explains why and offers the fix in one tap.

Open decision: the mismatch banner is informational, not blocking — Save/Update stays enabled. Real passbook figures can legitimately differ by a few rupees (rounding, a rate-change edge case Penny's model doesn't capture), and the person editing is usually transcribing a real document; forcing them to match Penny's number would fight the actual passbook. This is different from the gap-guard in §1, which does block — there the problem is a missing prerequisite record, not a legitimate value discrepancy. Flagging this distinction explicitly since the spec's wording ("should be blocked") could be read either way; recommend confirming before implementation.
Summary & open decisions
Recommendation: build all three pieces together (gap-guard + CTA re-seed + always-on calc banner) — they're one coherent feature, not three independent toggles, and the calc banner is what makes the gap-guard's fix path actually one tap instead of "go figure out the number yourself." Reuse PpfInfoModal's slate/violet aesthetic and the FY-end nudge's amber shell exactly as shown above rather than a new visual language — this screen already has enough distinct banner colors (violet=education, amber=action-needed, green=confirmed) that a fourth would blur the "what does this color mean here" convention the redesign already established.
Open items to confirm before implementation:
  1. Exact banner copy — wording above is a first pass; confirm tone (the gap-guard's "on hold until it's added" vs. something softer) before wiring real strings.
  2. Gap-guard scope confirmation — structural read says it applies to deposit/withdrawal/interest transactions dated after earliestMissingFy, but never blocks anything dated within/before the gap year itself. Confirmed against the spec's own wording; flagging once more since it's the crux of the whole feature.
  3. Mismatch = informational, not blocking (see §3's box above) — recommend confirming this explicitly since it's the one place this proposal reads the spec differently from a strict literal block-everything interpretation.
  4. A missing-history edge case — PpfInterestCalculationResult.basedOnIncompleteHistory already exists (true when Penny's own transaction record starts after the FY it's calculating, i.e. the account has real pre-Penny history never entered). Not shown as a separate banner state above to avoid multiplying variants unnecessarily, but the calc banner's copy should soften to "our estimate — based on only what's logged in Penny" whenever this flag is true, both in the fresh and matches/mismatch states.
  5. No new tracking doc — this is a portfolio/PPF feature, unrelated to docs/plans/real-device-testing-pass.md; if it needs its own implementation tracking doc, that's a suggestion for the user to decide, not something created here.
