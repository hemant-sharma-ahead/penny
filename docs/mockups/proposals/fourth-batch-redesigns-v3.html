Recommendation: ship all four sections as shown here.
  • §1. This is a real, if partial, improvement — 3 of 12 banks (including two of the most common in the app's likely user base, HDFC and ICICI) get a genuine brand mark instead of a generic building icon, with zero risk of a fabricated logo for the other 9. Ship it now; track the remaining 9 as a follow-up research task (their official brand pages, not Simple Icons, which doesn't carry them).
  • §2 & §3. Consolidating "create" into one screen-level button rather than a per-row/per-tile inline option is the same "one capability, one control" principle the Backup & Restore incident codified — creating an account or category is a single, general-purpose capability that doesn't need N near-identical inline copies of its own form scattered across rows. Reusing the real AccountFormModal/CategoryEditorModal instead of bespoke inline fields also means any future improvement to account/category creation (a new field, a validation rule) lands in the import flow for free.
  • §4. The scrub bar's value only holds up if it truly reaches every transaction, not just a recent window — a longtime user with 10+ years of data hitting a dead end at chip #24 would be worse than the modal it replaced. Demonstrating the full 141-month scroll here is deliberately not just cosmetic.

Judgment calls & open questions for review

  1. §1 — single-colour approximation of ICICI's gradient mark. Simple Icons' ICICI path is rendered here in a single solid orange; ICICI's actual real-world usage is often a two-tone orange/maroon gradient. Using the flat single-colour SVG as-is (rather than hand-building a gradient fill) matches "use these verbatim" from the source package — flagging as a deliberate simplicity-over-fidelity choice, not an oversight.
  2. §1 — where bankId actually drives the logo. AccountFormModal.tsx's optional Bank (optional) field already writes Account.bankId for SMS Tracking's matching — this mockup assumes the Cash Flow tile's icon would key off that same field once implemented, not a new one. Not yet wired in code; just noting the natural integration point.
  3. §2 — "+ Create Account" placement. Put at the very top of the stage (above every bucket), per the direction given, on the theory that a first-time importer with zero matching accounts needs it before they've even opened a bucket. An alternative (a same button repeated inside each bucket) was considered and rejected as re-introducing per-location duplication of the same capability — exactly what this round is fixing.
  4. §2 — newly-created account surfacing. Modeled as appearing in the very next "Map Existing" row's alt-pill list (via "Not this account?") with a green "NEW" tag. A real implementation should also make it the top-ranked option in that list's default ordering, not just present — not modeled here since the underlying ranking heuristic isn't part of this UI proposal.
  5. §3 — Transfer's mandatory destination field when no other account exists yet. ImportCategorizeModal.tsx already shows "No other accounts yet — add one from Accounts, then come back" in this case; kept that exact real copy here rather than inventing new wording.
  6. §4 — "currently-viewed year" vs "today's real year". Interpreted the chip-label rule relative to the currently selected month's year (so scrolling into 2019 and selecting a 2019 month makes other 2019 chips show month-only, while 2026 chips reintroduce their year) — not literally today's calendar year. This reads more consistently while scrubbing through history; flagging the interpretation explicitly since the request was slightly ambiguous between the two.
  7. §4 — earliest-transaction-date scan. No existing helper computes this — the real implementation needs a simple one-time Math.min over every transaction's date (cached, not recomputed per render). Nothing fancy; just not free today. This mockup illustrates the range with a fixed Nov 2014 floor rather than a computed one.
