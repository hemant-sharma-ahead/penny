Bank Balance Sync — Mockup Gallery v1

Grounded in docs/plans/bank-balance-sync.md §6 and the worked numbers in bank-balance-sync-simulation.html. Every example below uses the same HDFC savings ledger from that simulation (opening ₹50,000 on 1-Apr) — no invented numbers. This is mockup-only; nothing here has been built.

Scope note on "3 distinct directions": the plan asks for 2–3 genuinely different directions for "the new surfaces," not a full 3× repeat of all 7. The real design tension is concentrated in surfaces 1+2 — the checkpoint-diff marker and the persistent account-level "unverified" state — because that's where subtlety-vs-clarity tradeoffs actually diverge. Sections A/B/C below present three structurally different answers to those two. Surfaces 3–7 (gap banner, skipped count, opening-balance/anchor prompts, ambiguous transfer) are each shown once, because the design space there is narrower — they mostly reuse existing Banner/Modal/inline-form patterns already established in bank-statement-import-v1.html and SetupStep.tsx, so alternate "directions" would mostly be placement variants, which the project's own convention says to avoid manufacturing for their own sake. Flagged explicitly in case you want alternates there too.
  • Numbers used throughout: §7b/7c's "missing 30-Apr interest" scenario (last agreeing = 25-Apr Groceries ₹106,800, first disagreeing = 3-May Salary, gap +₹120) is the centerpiece example for surfaces 1/2/7-copy. §7d's wrong-opening-balance scenario (flat +₹1,000 from day one) is the "flat" counter-example for the diagnostic-copy surface. §11b's gap wording, §11a's skipped-count wording, §10a/§14/§14b's anchor numbers, and §13's HDFC↔ICICI ambiguous-transfer example are used verbatim where the plan already gives exact copy.
  • One live bug this proposal fixes as a side effect: today's DoneStep.tsx "Reconcile now ›" nudge navigates to the Accounts list and stops there — ReconcileModal only opens for cash/wallet accounts (RECONCILABLE in AccountList.tsx), never for the bank accounts this nudge actually fires for. It's a dead-end today. The new persistent "unverified" surface (§2 below) replaces this nudge entirely and actually goes somewhere on tap.
  • Scope check worth a decision: AccountList.tsx's STATEMENT_IMPORTABLE set includes credit_card alongside bank — but the plan (§3 decision 1, §8) explicitly scopes checkpoints to bank accounts only, credit cards deferred. None of the surfaces below should appear on a credit-card account until that's separately designed; worth confirming that's the intended v1 boundary before implementation.

Tradeoff: cheapest to build, zero new screens — but risks being too quiet. CDirection C — Hybrid: Compact Status + Drill Into the Real List ★ recommended
A short diagnostic snapshot (just the two rows that matter — last agreeing / first disagreeing — not the whole ledger) surfaces from the same persistent badge as Direction A, but tapping "Investigate" opens the account's existing transaction list (no new screen) scrolled to and highlighting exactly those two rows with Direction A's inline markers. Best of both: a real, unmissable entry point (unlike A), reusing infrastructure instead of a whole new screen (unlike B).

Why this is the recommendation:
  • It's genuinely unmissable — the snapshot sits right where the user already looks (the account modal they open to check a balance), not buried behind an extra tap into a new screen.
  • It reuses real infrastructure (EntityTransactionsModal + TransactionsTab, already virtualized, already the account's canonical transaction view) instead of standing up a parallel ledger-table screen — smaller surface area to build, test, and keep in sync later, and matches "reuse patterns the user already knows" (§1 of the guidelines).
  • The "View full reconciliation table ›" link at the bottom is a deliberate escape hatch to Direction B's table for the minority of users who do want the literal ledger view (e.g. after multiple mismatches stack up) — so B's idea isn't lost, just demoted to progressive disclosure.
  • Honest tradeoff: this is more work than A (needs the modal extended with the banner + scroll-to behavior) but meaningfully less than B (no new screen, no new nav route, no full checkpoint-table renderer needed for v1 — can be added later behind that same link if it turns out to be wanted).

5Diagnostic copy — the two failure signatures, side by side

Signature comparisoncopy reference
Both use the same two real scenarios from the simulation — a missing 30-Apr interest credit (steps in) vs. a ₹49,000-instead-of-₹50,000 opening balance (flat from day one).
Steps in partway through
Every checkpoint agrees until 25-Apr, then jumps to a steady +₹120 from 3-May onward and never changes again.

What it means: a single missing or duplicate transaction, strictly between those two dates — not your opening balance. (§7b/7c)
Flat from day one
Every checkpoint is off by the same +₹1,000, all the way back to the very first checkpoint — never zero, not even at the start.

What it means: check this account's opening balance — it may have been entered wrong when the account was set up. (§7d)
 Caveat surfaced inline whenever the "flat" copy shows: "This only rules out a missing transaction if your opening balance was itself verified against an earlier statement — if it was a typed-in guess, importing an even earlier statement is the only way to confirm it."
