Expense Import — new "Import Progress" screen, v1

New screen for apps/mobile's CSV/Manual Expense Import (docs/plans/csv-expense-import-redesign.md), inserted where tapping "Import" on TransactionsStage.tsx today goes straight into a blind write with only a button spinner and no guard against back-navigation mid-write — a real bug found in testing. One screen, three states (Pre-start → Importing → Complete), grounded in TransactionsStage.tsx's real Import button/banner and DoneStep.tsx's real completion layout (reused verbatim for the Complete state, not redesigned). Mobile-only — apps/web-react is frozen. Proposal only; no app code touched yet.

Recommendation: build this as one component with three internal states (not three routes) exactly as scoped — it's the cleanest match for useImport.ts's existing "nothing until commit" model (§3.1 of the redesign doc) and needs no new navigation entries. Keep the progress count/bar driven by the same per-row loop commitAndImport() already runs (just surfacing its existing counters instead of a single opaque await), and reuse ConfirmDialog.tsx/DoneStep.tsx verbatim rather than building new primitives for either.
Calls made while building this mockup — flagged, not silently decided:
  1. Whether this is a new distinct wizard step, or the existing "Done" step's content moved inside a new preceding screen. The task description's State 3 ("reuses DoneStep.tsx's content", "Go to Expenses" as plain nav) reads as this screen absorbing Done's role rather than sitting in front of a separate Done screen — that's what's mocked up here (one screen, header title flips from "Importing" to "Done" as state advances, matching today's real Done header exactly). This has real implementation consequences — useImport.ts's Step union, ImportPage.tsx's backTarget/stepSequence/showWizardChrome maps, and whether DoneStep.tsx gets deleted vs. kept as a still-separate file whose JSX this new component copies — needs explicit confirmation before implementation, not just inferred from this mockup.
  2. "Draft" badge dropped once Importing starts (state 2). The badge's whole meaning is "nothing saved yet" (redesign doc §3.1/§4) — that's no longer true once the write loop is progressively committing rows, so it's removed rather than kept showing a now-false claim. Not explicitly called out in the task description; my own inference from what the badge is supposed to mean.
  3. Cancel button variant: secondary (bordered), not ghost. The task says "secondary/ghost weight, not primary" — either satisfies "not primary". Chose secondary (real bordered Button variant) over plain ghost text-only, since Cancel is a meaningful, always-available action here (the only other control on screen besides the progress display itself), not a subordinate/rarely-used one — a pure text-ghost link risked reading as too easy to miss.
  4. "Stopped early" tint: warning/neutral, not danger. Cancelling is a deliberate, successful user action (nothing failed), so it gets the same warning-amber treatment DoneStep.tsx already uses for its own "partially complete" case — not danger-red, which is reserved for actual row failures (hasFailures in the real component).
  5. Undo remains available in both Complete framings. Not a new decision — DoneStep.tsx's real condition (activityLogId && succeededCount > 0) already covers both a full finish and a stopped-early partial commit identically, since either way real rows were written and the same one-click whole-batch undo applies. Carried through unchanged, not redesigned.
Worth flagging for the mobile-developer at implementation time (not a design question):
  1. Locking back-navigation during Importing needs to cover more than the header chevron shown here — Android hardware back and iOS's edge-swipe gesture both need interception too (e.g. beforeRemove/BackHandler), or a determined user can still leave mid-write through a path this mockup can't depict.
  2. The estimated-duration and ETA figures ("~45 seconds", "~15 seconds left") are illustrative placeholders — the real implementation needs an actual estimate (e.g. rows-remaining ÷ observed rows/sec so far) rather than a hardcoded string.
