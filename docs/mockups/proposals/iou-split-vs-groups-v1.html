Personal IOU split amount vs. Groups — should IOU handle both?

Triggered by a real question: if the Lent/Borrowed panel gets an editable amount (so a ₹500 cab can be logged as a ₹250 debt, not the full ₹500), does that start blurring into what Groups already does — and should the two roommates in this example have one combined "who owes whom" number, or stay two genuinely separate ledgers the way they are today? Three directions below, grounded in PersonLedgerView.tsx, GroupDashboard.tsx, and ExpenseForm.tsx's real current screens — nothing here is built yet.

2Direction A — editable split amount, IOU and Groups stay fully separate
Fixes the "can't log a partial debt" gap only. IOU keeps its current identity — a simple, informal, one-off 1:1 ledger — and never learns Groups exists.

This adds one editable amount field, prefilled with the full amount, plus a "Split evenly" shortcut chip for the common 50/50 case — still a single free-typed number underneath, so any ratio works, not just half.

One Expense row (₹500) and one LedgerEntry row (₹250), joined only by linkedTxnId — never the same field. Bank import/ reconciliation, the account's balance, budgets, and Analytics only ever read Expense.amount — they have no idea a split even happened, so nothing about reconciliation changes. The Lent panel's amount field writes to the LedgerEntry alone (via seedIouFromExpense/reconcileExpenseLink); it never touches Expense.amount. This is the opposite direction from EntryForm.tsx's standalone "Add IOU" flow, where the entry amount is the money movement and, if recorded, becomes the transaction's own amount too (there's no separate "full cost" in that flow to begin with).

Cheap, low-risk, fixes the actual reported gap, and doesn't restrict the amount to any particular fraction — full amount remains the default, any other number is one edit away. Doesn't address the "two disconnected totals for Ramesh" problem from §1 — Direction C adds that on top.
3Direction B — merge personal IOU into Groups entirely
The other extreme: retire the Lent/Borrowed panel, route every person-money interaction — even a single ₹500 cab — through a Group, since Groups already computes real splits.
What this would actually require: Person (offline, local-only, created by typing a name) would need to become — or be backed by — a Group (membership records, roles/admin, the sync/fold-engine machinery in workers/groups). Every current personal-IOU screen (PersonLedgerView, EntryForm, SettleUpModal) would be replaced by Group screens for what's today a zero-setup, fully offline feature.

Real friction for the common case: a one-off ₹500 cab now needs a named, membered Group before you can log it — for something you might never split with Ramesh again. Groups' data model (membership, admin roles, multi-device sync) is genuinely heavier machinery than "I paid, note that Ramesh owes me ₹250" needs. Not recommended — this solves the "one combined number" problem by force-migrating every quick 1:1 debt into the wrong-weight tool.
4Direction C — recommended: stay separate, bridge the visibility
Ship Direction A's split amount as-is. Keep the two ledgers structurally separate — different data models for a real reason (one-off informal debt vs. a persistent multi-party pool) — but when the same human exists in both, surface that fact instead of staying silent about it.
Uses the schema link that already exists but sits unused — GroupMember.linkedPersonId. Once a Person is linked to a Group member (via the existing "Promote to Group" flow, or a lighter new "This is the same person as…" match), PersonLedgerView shows a small read-only note with that Group's current balance alongside — no merged total is stored anywhere, purely a display-time join of two numbers that both already exist.
Can one Person link to more than one Group? Yes, structurally — but not through any existing flow yet. Checked packages/core/src/core/db/types/index.ts: `linkedPersonId` lives on GroupMember (line 997), not on Person — so it's naturally many-to-one. Ramesh's Person row can be pointed at by his "Flat 4B" GroupMember row and separately by his "Trip to Goa" GroupMember row, with no conflict — nothing about the schema caps it at one Group. The real gap: grepping the codebase, the only place that ever writes linkedPersonId today is PromoteToGroupWizard.tsx's one-way "Promote" action — which also sets Person.promotedToGroupId and archives the Person. That flow is a migration (this Person's ledger becomes this one Group), not a general-purpose match, so it doesn't actually give you a live, still-active Person linked to two independent Groups today. Direction C needs a second, lighter action — "Link to an existing Group member" (no archiving, no ledger migration, just sets `linkedPersonId` on that one GroupMember row) — repeatable per Group, which is what makes the multi-Group case below possible.

Recommendation: Direction C. Keep personal IOU and Groups as two deliberately different tools — they answer different questions ("what does this one person personally owe me, informally, right now" vs "what's the running settle-up on this shared pool of costs among a fixed set of people"), and Direction B's cost of forcing every debt through Group membership isn't worth paying just to get one combined number. Ship §2's split-amount field on its own first — it's the actually-reported gap, is fully non-restrictive (full amount stays the default; any other split is one edit away), and never touches the real Expense.amount that bank import/reconciliation/budgets/Analytics rely on — that number stays exactly what was paid, always. The linked-note in §4 is real value but needs a new, lighter "Link to an existing Group member" action (distinct from the existing archiving "Promote" flow) before it can support a Person who's an active member of more than one Group at once — treat that as a fast follow-up, not a blocker for shipping the split amount.
  • Cross-platform: apps/web-react's ExpenseForm.tsx has the identical person-only Lent panel and the identical two-unlinked-ledgers gap — frozen, so nothing here proposes touching it, flagging only that mobile and web already agree on the current gap.

Judgment calls & open questions for review

  1. §2 "Split evenly" scope — modeled as always a straight ½, regardless of how many people are actually involved (the transaction itself has no participant count, unlike a Group expense). If a 3-way informal split is common enough to matter, the chip would need to ask "split between how many?" instead of assuming 2 — flag if that's a real case, otherwise ½ covers the roommate scenario that prompted this.
  2. §2 label — used "Amount owed" rather than "Their share," to stay correct for both Lent (they owe you this) and Borrowed (you owe them this) without two different field labels.
  3. §4 matching mechanism — confirmed linkedPersonId lives on GroupMember, so one Person can be matched to any number of Groups with no schema change. But the only code that writes it today is the archiving "Promote to Group" flow — a genuinely new, non-archiving "Link to an existing Group member" action (matching by name, with confirmation, reusable per Group) needs its own small design pass before §4's multi-Group banners are real, not just mocked here.
  4. §4 combined-total pill — shown as an idea, deliberately kept optional/secondary, and gets weaker the more Groups pile up: summing a one-off debt with two different Groups' running pools implies they're one number when they're really three separately-settling ones (a personal debt clears in a single payment; each Group's pool keeps accruing on its own schedule). Worth a second look before committing to it, separate from the core recommendation.
  5. §2/§4 amount vs. transaction, confirmed — the split field only ever writes to the LedgerEntry (via reconcileExpenseLink); the linked Expense.amount (₹500) is never touched by it, so bank-statement reconciliation, account balances, budgets, and Analytics all keep reading the real amount paid regardless of what split value is entered. The reverse flow — EntryForm.tsx's standalone "Add IOU," where the entry amount doubles as the recorded transaction if "record as transaction" is on — has no separate "full cost" to preserve in the first place, so this split-field concern doesn't apply there.
