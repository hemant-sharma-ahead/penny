Recommendation: ship all four sections as shown here.
  • §1 & §4. Already approved in v4, unchanged here — ship as-is.
  • §2. The side-by-side card is the right call over v4's plain dropdown row — it makes the match a real, glanceable comparison (raw CSV text vs. the actual matched account, with its real logo) instead of a single-line form control, and it directly answers "is this side clearly tappable?" with a bordered chevron-down pill rather than looking like inert label text. Requiring an explicit Confirm tap (not just picking from the list) matches the screenshot and gives one honest, visible "yes, this is right" moment per row — worth the one extra tap for a money-matching decision.
  • §3. Reverting fully to the real accordion + modal pattern here was the right instinct — Categories already has a working, familiar interaction (expand to inspect, one modal to resolve); redesigning it alongside Accounts' pill format would have meant learning two different resolution patterns on the same screen for no real gain. Keeping only the Create→CategoryEditorModal swap isolates the one genuine improvement without touching what already works.

Judgment calls & open questions for review

  1. §2 — Confirm is a real extra step beyond today's real bucketing logic. The actual AccountsStage.tsx/bucketForAccount() today moves an "existing"-kind row straight to the Ready bucket the moment any account is picked — there's no separate confirm gate for that kind (only "create" has the "Looks good, use this" acknowledge step). This mockup's explicit Confirm/Skip buttons reintroduce a confirm gate for "existing" mapping too, per the screenshot/spec. Flagging clearly since a real implementation would need to decide: change the real bucketing rule to match (add a confirm gate to "existing" the way "create" already has one), or keep today's auto-ready-on-pick behavior and treat the Confirm button as answering yes immediately after a pick with a one-tap affordance only for the no-guess case. Recommend the former for consistency between kinds, but calling it out rather than deciding silently.
  2. §2 — no explicit "un-confirm" affordance once a row shows the green line. The only way to change a confirmed row is tapping its right-hand pill again to reopen the picker, which reverts it to the Confirm/Skip state until re-confirmed. There's no separate "Skip" reachable directly from an already- confirmed row without going through the picker first — reasonable, but flagging as a minor gap versus a fully-specified interaction.
  3. §2 — merge/fuzzy-match sub-features not re-modeled here. Same as prior rounds: AccountsSection.tsx's same-account-written-differently fuzzy-merge and card→account merge suggestions are orthogonal to this card-format change and aren't depicted — a real implementation shouldn't assume they were designed away.
  4. §3 — auto-opening CategoryEditorModal on "Create." Modeled as: tapping the "Create" KindTile (an active choice, switching kind) immediately opens the editor; if the tile's own suggestion was ALREADY "create" when the modal opened (an unconfirmed smart guess), the modal instead shows a quiet summary row ("New category: X · Group [Edit ›]") rather than force-opening a second modal on top of the first the instant it renders. This seemed like the least jarring reading of "opens … when the user picks create," but flagging as a judgment call — an alternative always auto-opens the editor on any create state, including the passive default.
  5. §3 — bulk-select/partial-selection fidelity simplified. The real CategoryTile.tsx/ImportCategorizeModal.tsx support an opt-out row-checkbox model gating a partial-selection Apply to "existing only," plus a full Lent/Borrowed (IOU) panel for IOU-mandatory categories. This mockup shows simple per-row checkboxes feeding the "Categorize N selected" count and restricts the KindTile grid to "Existing" only on a partial selection (matching real behavior), but omits the IOU panel entirely as orthogonal to this round's ask (Categorize-modal create-flow only).
  6. §4 — earliest-transaction-date scan. Unchanged open item, carried from prior rounds — no existing helper computes the real floor date; still illustrated with a fixed Nov 2014 floor rather than a computed one.
