5. Three things hiding in this same data worth deciding on

1Cash withdrawals that were already manually logged never become Transfers Both ATM withdrawals (5-Apr −5,000, 8-May −3,000) matched an already-existing plain Expense (Cashew's "Cash withdrawal", MoneyView's "Cash Withdrawal - ATM") — not a fresh unmatched row. The cash-withdrawal-code detector (cashWithdrawalCodes.ts) only offers to classify a row as a Transfer when it's building a new transaction from an unmatched statement row; it never looks at a row that turned out to already match something. So these ₹8,000 total stay permanently mis-typed as plain bank expenses, and the linked cash account is under-credited by ₹8,000 forever — even though the bank account's own balance is fine. This only shows up because we're now specifically checking cross-account correctness, not just the bank account in isolation.
2A near-miss silently creates a duplicate instead of a "new" row Suppose the user had actually logged the SMS charge in Cashew — but 6 days late, dated 26-Apr instead of the real 20-Apr value date (very plausible: people notice a small debit days after it posts). The matcher's date window is ±3 days, so this row would not find that existing entry, get treated as New on import, and get committed — leaving two ₹150 debits in Penny for one real transaction. The end-of-period balance check would then show a ₹150 mismatch, but nothing points you at which row is the duplicate — you'd have to eyeball the ledger. The same failure mode applies to amount near-misses (user typed 150 as a round guess; real fee was 149.50 exactly) — exact-amount matching also fails there.
3A wrong opening balance is invisible in a single end-of-period check Now imagine everything above happened exactly as the happy path (Section 4) — final Penny balance lands on ₹1,79,330, matching the real closing balance perfectly — except the account's openingBalance was actually set to ₹49,000 on day one (a typo from months ago, unrelated to any of this) instead of the true ₹50,000. Every single transaction still matched correctly, nothing is duplicated — but Penny's true derived balance is ₹1,78,330, a flat ₹1,000 under the real ₹1,79,330. One end-of-period check just says "mismatch, ₹1,000" — indistinguishable from "you're missing a ₹1,000 transaction somewhere." Only a per-checkpoint history (was April's own closing balance already off by exactly ₹1,000, and March's, and every month before that too?) would point at the opening balance specifically rather than a missing transaction.

6. What this settles, and what's still open

Settled by the simulation: the core mechanism (derive-then-diff against the statement's own closing balance) genuinely works for the common case — this isn't a broken idea, the happy path is real. The three findings above aren't "the design is wrong," they're the specific edge cases the design needs to name and handle on purpose:

  • Finding 1 needs a decision: should a bank-statement row that matches an existing plain expense but itself qualifies as a cash-withdrawal code still prompt "this looks like a transfer — convert it?" — a retroactive reclassification path that doesn't exist today.
  • Finding 2 needs a decision: is a ₹1-tolerance, single end-of-period balance check enough of a safety net, or do we want the review screen to actively flag "this account still doesn't reconcile, here's the ₹150 gap" and require it to be resolved (find the duplicate, or accept a real unexplained variance) before the import can be marked "verified"?
  • Finding 3 is the strongest argument for the "verified-through checkpoint per account" idea from before — a single post-import diff can't tell a missing transaction apart from a wrong opening balance; a running history of checkpoints can, because a wrong opening balance shows up as the exact same offset at every single checkpoint forever, while a missing transaction shows up once and then resolves.

7. Per-transaction closing balance — visualized

The idea: don't store a computed balance per transaction (that's always derivable, so storing it would just go stale). Store the bank's own stated balance — but only on a transaction that genuinely came from, or was matched against, a real statement row with a balance column. A manually-entered Cashew row has none. The moment a bank-statement import matches that row, it gets enriched with the real number straight off the bank's own ledger. Call it a checkpoint: ground truth, immutable, never guessed, present only where we actually have it.

Then at every checkpoint — not just once at the end of an import — compare it against Penny's own running derived balance at that same point. The table below is that comparison, walked chronologically, for three versions of the same ledger.

Signature: flat from the very first checkpoint, never a step This is the tell. 7b and 7c both start at 0 and step away partway through. This one is never 0, not even at the very first transaction. That single distinction — "was there ever an agreeing checkpoint at all?" — is exactly what separates "go find the missing/duplicate transaction between two dates" from "go check the account's opening balance," and a per-transaction checkpoint history is the only way to tell them apart. A single end-of-period check (today's mechanism) genuinely cannot distinguish 7d from a ₹1,000 gap hiding somewhere in the middle.

One honest caveat, worked out fully in Section 14: this diagnostic only works if "the very first checkpoint" is itself independently verified (i.e. statement-backed), not just wherever Penny's tracking happened to start. A flat offset present from day one is equally consistent with "opening balance was wrong" or "opening balance was actually fine, we just never had anything earlier to check it against." Only backfilling to an even earlier, independently verifiable statement can actually settle which.

7e. One caveat worth flagging

Same-day, multiple transactions A statement's balance column is only meaningful in the bank's own row order. If two transactions land on the same calendar day, the checkpoint comparison is only reliable after the last one for that day — checking mid-day would require Penny to also preserve the bank's exact intra-day ordering, which it doesn't do today (transactions aren't otherwise sequenced within a day anywhere in the app). Practically: treat every same-day cluster as one combined checkpoint at day's end, not as N separate checkpoints. Doesn't break the idea, just means the "search window" in 7b/7c is expressed as "between end-of-day X and end-of-day Y," not down to the individual transaction, when multiple same-day rows are involved.

8. Does matching correct the transaction's date today? — checked the code: no.

Confirmed directly in apps/mobile/src/features/bank-import/useBankImport.ts: when a statement row matches an existing transaction, the commit step only writes a provenance record —

What happens today for a matched pair
await bankStatementImportsRepo.put({ ..., date: row.date, amount: row.amount, linkedTxnId: pair.expense.id }) — a separate provenance record, keyed by the statement's date/amount
The actual Expense record itself is never re-written. expensesRepo.put() is only ever called for brand-new transactions, never for matched ones.
So a Cashew entry logged 2 days late stays 2 days late, forever Today this is harmless — matching only needs "close enough" (±3 days), so a wrong-but-close date doesn't stop the match. But it breaks the moment you want day-bucketed checkpoints: a transaction that really happened 20-Apr but sits in Penny dated 22-Apr would get filed under the wrong day's checkpoint, producing a false one-day "gap" that isn't a real gap at all — just a stale date nobody ever corrected.
Proposed fix On commit, whenever a matched pair's dates differ (confident matches: matcher.ts's auto-pairs; user-resolved: the "possible" bucket), also update the Expense's own date to the statement row's date — the bank's date is the real one; Cashew/MoneyView's was always an approximation. Same logic extends to amount: confident auto-matches already require an exact amount, but a user-resolved "possible" match can have a small amount difference (that's part of why it needed a human to confirm it's the same transaction) — once confirmed, correct the stored amount to the statement's exact figure too, for the same reason. Neither needs a confirmation dialog — the user already confirmed "yes, this is the same transaction" by resolving the match; correcting it to the verified-accurate value is just finishing that action, not a new decision.

9. Preserving the statement's own order within a day

Once dates are corrected (Section 8), same-day transactions can go one step further than the end-of-day fallback in 7e. A bank always prints same-day rows in true chronological order. Proposal: a new field, something like Expense.reconciledSeq, set only on statement-linked transactions — its position (1st, 2nd, 3rd…) among that day's rows in the statement. Rule for when it's trustworthy:

Only when the day is "fully explained" by this statement If every one of Penny's transactions on a given day is either newly created from this statement or matched to one of its rows, reconciledSeq gives a real, checkpoint-verifiable intra-day order. If even one transaction that day has no statement counterpart (a genuinely separate manual entry, or an unresolved duplicate), its true position relative to the others is unknown — that day quietly falls back to end-of-day-only (Section 7e), rather than guessing.

Worked example — why intra-day order isn't just cosmetic

Illustrative example — small self-contained numbers, not the running 2-month ledger above

Balance carried into 8-May: ₹4,200. Two real transactions that day: a 09:14 ATM withdrawal (−₹3,000) and an 18:40 UPI refund credit (+₹2,000). Both orderings land on the exact same end-of-day balance — but tell very different stories about what actually happened during the day:

The end-of-day check alone would call both of these identical Same closing balance, so a per-day checkpoint sees no problem either way — and for pure sync-verification purposes, there genuinely isn't one. Getting the order right costs nothing extra once dates are already being corrected (Section 8) — it's the same statement data, just also keeping the row order it already comes in.

10. Retrospective imports — filling in history, and a real limitation

You're right that this needs first-class support — most new users will want to backfill months or years of history, not just start tracking from today. A few distinct situations:

10a. The very first statement ever imported for an account

This is exactly the moment to capture the true opening balance — per your earlier answer, by asking the user to confirm it (parsed from the statement's own header when we can find one, otherwise typed in), rather than guessing. Nothing unusual here; it's just the earliest point the "verified-through" idea has anything to anchor to.

10b. Backfilling a gap between two periods that are already checkpointed

Example: April+May are already fully reconciled (Section 4); March was never imported at all, still pure-Cashew, unverified

The user later finds and imports March's real statement. It recovers 2 forgotten transactions, and March's own final checkpoint (31-Mar) now lands exactly on the already-established 1-Apr opening figure (₹50,000).

The clean case — nothing downstream needs to change Because checkpoints are anchored to actual calendar dates, not import order, closing the March gap doesn't require touching April or May at all — they were already correct, and stay correct. This is the payoff of Finding 3's "verified-through" design being per-date rather than a single "latest import" watermark: gaps can be filled in any order, forwards or backwards, without disturbing what's already settled.
But it does need a rule: re-check forward, every time That April/May stayed unaffected here is a fact about this data, not a guarantee in general — inserting or correcting anything earlier in an account's history changes Penny's running balance for every date after it (opening balance and running totals are shared across the whole account). The safe rule: any retrospective import should trigger recomputation of checkpoint diffs for every later date too, not just its own range — cheap to do, and the only way to reliably catch the rarer case where a backfill actually does disturb something downstream (Section 10c is exactly that rarer case).

10c. The blind spot: two errors that cancel out are invisible to any balance check

Same March backfill, different starting condition

Suppose March's Cashew data was missing two things: a ₹300 refund (credit) it never logged, and a ₹300 fee (debit) it also never logged. Net effect on the month: exactly ₹0. March's end-of-month balance already matched perfectly — before anyone ever checked it against a real statement, purely by coincidence.

No checkpoint, at any granularity, would ever have caught this End-of-period, end-of-day, even a perfect per-transaction sequence — all of them are arithmetic checks, and the arithmetic was always fine. The only thing that can catch a "missing credit + missing debit that happen to cancel" is the review screen's row-by-row identity matching during the actual import (does a corresponding row exist for each statement line, not does the total match) — which is exactly why the review screen's matched/possible/unmatched buckets need to stay the primary defense, with balance checkpoints as a second, complementary layer — not a replacement for looking at the rows themselves. Worth being explicit about this limit rather than implying checkpoints alone are a complete guarantee.

10d. A statement even earlier than the one that set the opening balance

This turns out to be common enough to design for properly, not just flag — see Section 14, which works it through in full with real numbers, including a genuinely important twist.

11. Partial imports — two different things, both need handling

"Partial import" can mean two different things, and they need two different fixes.

11a. The user deliberately excludes some rows during review

The review screen lets you leave some unmatched rows out of the "add as new" bulk action — reasonable (maybe it's a duplicate, maybe it's not actually yours). But today nothing records that this happened. Three weeks later, nobody — not the user, not Penny — can tell "this row was never in any statement" apart from "this row was seen and deliberately skipped."

Proposed fix Every import batch should keep a durable record of what it actually decided for every row it saw, not just the ones that got committed: matched (N), added new (N), excluded — user chose not to add (N). Surface that count on the commit confirmation ("13 rows found, 11 added, 2 skipped") and keep it visible later in the batch's own history entry, so a skipped row is a visible, intentional decision — not indistinguishable from a gap nobody ever looked at.

11b. The statement file itself only covers part of a period

A user downloads "March statement," but the bank's export tool only gave them 1–15 March (a partial download, a paginated export, a re-issued statement that only covers from account reactivation). Every row in the file gets imported cleanly — the import itself isn't wrong — but the user, and Penny, might both believe "March is done" when only half of it is.

Proposed fix: track covered date ranges, not just import events Per account, keep a list of { start, end } ranges — one per completed import batch, taken from the actual min/max date found in that file, never assumed from a filename or the user's stated intent. Before finalizing any import, check it against the account's existing ranges:
SituationWhat Penny should say
New range picks up exactly where the last one endedNothing — this is the expected case, import proceeds silently.
New range leaves a gap (e.g. last import ended 15-Mar, this one starts 1-Apr)⚠ "There's a gap between 16-Mar and 31-Mar this account has no statement for — was that period genuinely empty, or is there a statement you haven't found yet?"
New range overlaps an existing oneNot an error by itself (see Section 15) — just proceed; matching will mostly land on "already matched."

This one data structure — a simple list of covered date ranges per account — is also exactly what's needed for the "verified-through" idea from Finding 3, for detecting the March/April continuity question from the very first discussion, and for Section 14's backfill-anchor logic below. Worth building once, used in all three places.

12. "Extra" transactions the statement doesn't explain — don't cry wolf too early

Your scenario: a transaction sits in Penny with a slightly wrong date — say entered as 31-Mar when the real bank value date was actually 1-Apr, a very common near-month-boundary slip. When March's real statement gets imported, nothing in it matches this row (rightly — the real transaction didn't happen in March). Today's matcher would call this a "lone wolf": a Penny transaction this statement doesn't explain.

Flagging it immediately would be wrong here This transaction is about to be explained perfectly by April's statement — it's dated 1-Apr for real, within the existing ±3-day match window of the Penny row dated 31-Mar. Flagging it as "suspicious" during March's import would just be noise the user has to dismiss, for a non-problem that resolves itself one import later.
Proposed fix: defer, using the same date-range data from Section 11b Only escalate a lone wolf to "needs review" once an import whose own covered date range unambiguously should have explained it — including the ±3-day grace window — has come and gone without matching it. A lone wolf dated within 3 days of the current statement's start/end boundary gets a soft "provisional — pending the adjacent period" status instead of an immediate red flag; the very next adjacent import either resolves it silently (the common case, your scenario) or, if it still doesn't match, that's when it becomes a real, escalated flag — because now two statements in a row have had the chance to explain it and neither did.

13. Multiple accounts & inter-account transfers

New illustrative example — HDFC (checking) and ICICI (savings), same user

Important nuance: this matters for reporting accuracy, not for the balance-sync guarantee itself Even if the user never confirms the link and both sides stay as independent plain expense/income entries, each account's own balance still reconciles perfectly against its own bank statement — HDFC really did lose ₹20,000, ICICI really did gain it, and each account's own checkpoint math doesn't care whether the two rows are linked. What linking actually fixes is double-counting in whole-portfolio reporting: an unlinked pair shows up as +20,000 "income" and −20,000 "expense" in cash-flow analytics for a transfer that was never real income or spending. Worth being precise about this distinction so the design doesn't overclaim that unlinked transfers threaten the core guarantee — they don't; they threaten a different (also real) thing.
A genuine ambiguity: two same-bank accounts, coincidental same-day/same-amount activity If a user holds two accounts at the same bank (or the transfer amount happens to coincide with an unrelated transaction elsewhere), the "possible transfer" suggestion could have more than one equally-plausible candidate — e.g. ICICI also independently received an unrelated ₹20,000 from someone else that same day. This needs to surface as a choice ("this might be linked to one of these 2 transactions — which one, or neither?"), never an auto-link, exactly the same caution the existing suggestPossibleTransfer doc comment already takes ("dismissible-suggestion-only," never automatic).

One realistic wrinkle that doesn't break anything: banks often bill a transfer as two separate lines on the sending side — the ₹20,000 transfer itself, plus a small NEFT processing fee (say ₹5) as its own line. The ₹20,000 legs match and link as a transfer; the ₹5 fee is genuinely one-sided (correctly recorded as a plain HDFC expense) — that's not an app quirk, that's just how the bank itself bills it.

14. The opening-balance anchor can move backward

New illustrative example, building on your 2018-vs-2020 scenario

Today, Account.openingBalance has no explicit "as of" date — it's implicitly "before every transaction that exists," which only stays true as long as nobody ever adds a transaction earlier than whatever date the user had in mind when they set it. Backfilling breaks that assumption on purpose. Proposal: give it an explicit paired date, openingBalanceAsOfDate, and let backfilling to an earlier statement move both.

14b. The uncomfortable case — the backfill disagrees with the existing anchor

Same backfill, except the real 2022–2023 statements imply 1-Jan-2024 should have been ₹52,000, not the ₹50,000 the account was originally set up with (which, remember, was never itself checked against a statement — just typed in from memory/passbook at setup time).

This is the direct answer to the caveat added to Section 7d 2024 and 2025's checkpoints looked perfectly clean the entire time (flat, agreeing, no drift) — because there was nothing earlier to compare against, "day one" of tracking was the untested assumption. Only backfilling to an independently-verifiable earlier point exposes that the original ₹50,000 may have been wrong by ₹2,000 all along, silently carried through every checkpoint since. Once found, this needs the same recompute-forward rule as Section 10b (re-check every later checkpoint), except here the answer is "yes, they all need to shift by ₹2,000" rather than "no change needed" — the two 2024–2025 example scenarios in this doc are genuinely indistinguishable from Penny's point of view until an earlier anchor is available to settle it. Resolution still needs a human: is the ₹2,000 a real backfill defect (missing/duplicate row in the new 2022-23 import — check the review screen per Section 10c), or was the original setup guess simply off? Penny can narrow it, not decide it.

15. Re-importing the same statement twice

Worth checking directly rather than assuming: useBankImport.ts already tracks which existing expense each match "claims" (referenced.add(pair.expense.id)) so the same existing transaction can never be claimed by two different statement rows in one import. Re-uploading April's file a second time weeks later should, by that same mechanism, land every row as "matched" against its own already-linked counterpart from the first import — zero new rows, a safe no-op, even when a day has two genuinely identical ₹500 UPI payments (each still claims exactly one of the two existing candidates).

Already safe by design — one convenience worth adding anyway Correctness doesn't need a fix here. But a user backfilling years of statements is quite likely to accidentally re-upload a file — a quick pre-check against the covered-date-ranges list from Section 11b ("this file's range overlaps an import from 3 weeks ago — expect mostly matches") would save them a full trip through the review screen for something that's going to resolve to "0 new" anyway.

16. Other scenarios considered, briefly

  • Reversed/failed transactions (a debit reversed by the bank a few days later) — no special handling needed. Both legs are genuine, independent statement rows; the checkpoint model already treats them correctly as two ordinary transactions.
  • The same bank changing its export format over time (different columns/headers year to year) — a parsing-robustness problem, not a balance-sync one; already partly addressed by the header-row detection work done for PPF/Excel imports elsewhere in the app.
  • Credit cards, if this is ever extended there — flagged only as a footnote since you've scoped this to bank accounts: a card's balance moves in the opposite direction (spending increases what's owed) — any shared sign convention built for savings/current accounts would need explicit inversion, not an assumption it "just works" the same way.

17. Checkpointed transactions must stop being match candidates

Your example, worked through exactly: 31-Mar has a ₹240 expense, matched and checkpointed during March's import. April's real statement independently has its own, completely unrelated ₹240 transaction on 2-Apr. 2-Apr is within the ±3-day window of 31-Mar, and the amount is identical — today's matcher has no way to know the 31-Mar row is already "spoken for" by a different, earlier statement, so it's a live candidate.

Proposed mechanism — two-tier matching per row Tier 1, exact provenance lookup: normalize the incoming row's date+amount+narration and check the account's own import-history table for an identical row already recorded. A hit means this exact statement (or an exact reissue of it) was already processed — treat as matched, no fuzzy logic needed. This is also what correctly makes Section 15's "same file re-imported twice" case work.

Tier 2, fuzzy matching — but only against transactions that don't already have a checkpoint: everything else runs through the existing date-window/amount/narration matcher as today, with one added filter on the candidate pool: any expense that already carries a checkpoint from a previous import is removed from consideration entirely, in both the confident-auto-match path and the "possible match" human-review path. Only genuinely still-open transactions (raw manual/Cashew/MoneyView entries never yet verified against any statement) remain eligible.
One accepted limitation, in the same spirit as Sections 10c/10d If a bank ever reissues a corrected version of an already-checkpointed statement (say, fixing a value-date typo from 31-Mar to 30-Mar for that same ₹240 line), Tier 1 won't recognize it as the same row (the date changed) and Tier 2 won't consider the old checkpointed entry either (it's excluded) — the corrected row would come in as a second, duplicate "new" entry rather than correcting the original. Genuinely rare (banks reissuing statements over a data-entry correction), and not something to solve automatically — flagging it as a known gap that would need an explicit "re-verify this already-checkpointed period" action rather than happening silently through ordinary import.
