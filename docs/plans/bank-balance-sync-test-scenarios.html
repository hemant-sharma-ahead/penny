Bank Balance Sync — On-Device Test Scenarios

Six synthetic CSV fixtures + a recommended import order that together exercise every stage of the plan. Import them in the order below and compare what actually happens against what's written here — any deviation is either a real bug or something worth discussing.

Step 1 — Import Cashew (April)

Create/select an HDFC Savings account (type bank) if you haven't already, with no opening balance set yet. Import cashew-april-synthetic.csv — map Date/Title/Amount (a single signed-amount column; positive = income, negative = expense).

Expected 5 rows, all new (nothing to match against yet). No balance column was mapped (Cashew has none) — so no checkpoint gets attached to any of these rows, no opening-balance prompt should appear (bank-statement-import specific, and this file has no balance column to suggest one from anyway), and no gap-detection banner (first import for this account). The 5-Apr "Cash withdrawal" row stays a plain expense for now — deliberately, so Step 3 can demonstrate the retroactive cash-transfer prompt.

Step 2 — Import MoneyView (May)

Import moneyview-may-synthetic.csv into the same account. This fixture was rebuilt 2026-08-09 to match a real MoneyView export a user shared (structure only — no real values reused) — it's far richer than a typical bank statement: Date, Type, SubType, Txn Type, Payment Type, Merchant/Receiver/Sender, Category, Bank Name, Account Id, Account Type, Credit, Debit, Balance, Outstanding, Available Limit, Notes. Map Date/Merchant/Receiver/Sender/Debit/Credit. Note the date format is YYYY/Mon/DD HH:MM:SS (e.g. 2026/May/03 16:42:48) — a real, different-from-DD/MM/YYYY format worth confirming the date-format auto-detector actually handles correctly, given the exact class of bug (locale-guessing on an ambiguous numeric date) that was just found and fixed elsewhere in the CSV-expense-import flow.

Do not map the Balance column here — and here's the real reason why (corrected 2026-08-09) The original version of this fixture invented a "MoneyView's balance disagrees with its own arithmetic" scenario — the real file shows something simpler and just as disqualifying: for ordinary UPI/bank rows, the Balance column is just 0, essentially unpopulated. MoneyView only fills in a real running balance for certain linked sub-accounts (a debit card, in the real sample), not for regular transactions. So the practical lesson is even more basic than "it's wrong" — for most rows, there's usually nothing meaningful there to accidentally map in the first place. Confirm the app doesn't do anything strange if you map a Balance column that's entirely `0`/blank across every row (it should behave the same as if no balance column were mapped at all — no checkpoints, since there's no real value to attach).
Expected (Balance column left unmapped, as it should be) 4 rows, all new. No checkpoints attached (no balance column mapped). The 8-May "Cash Withdrawal" row also stays a plain expense for now, same reasoning as Step 1.
A bigger structural finding, not something this fixture tests directly The real MoneyView file this was rebuilt from interleaves THREE different sub-accounts in one export — a bank account, a linked debit card, and a "cash" pseudo-account — distinguished only by its own Account Id/Bank Name/Account Type columns. Neither this app's bank-statement importer nor its CSV-expense importer currently has any notion of "one file, multiple destination accounts" — both assume one file maps to one Penny account. Worth deciding whether that's in scope for either importer, separately from this testing pass.

Step 4 — Backfill: import the earlier HDFC statement (January–March)

Import hdfc-statement-jan-mar-synthetic.csv into the SAME HDFC account — a statement covering a period entirely BEFORE your current opening-balance anchor (1-Apr-2026).

Expected — anchor-shift prompt (Stage 3, §14a clean case) Because this file's own date range starts earlier than the account's current anchor, you should get the anchor-shift flow instead of the ordinary review screen. This file's own implied opening balance (1-Jan-2026) is ₹20,000, and its own transactions net to exactly +₹30,000 by 20-Mar — landing exactly on the ₹50,000 anchor you already confirmed in Step 3. This should surface as the clean, agreeing case: no disagreement to resolve, just confirm the new, earlier anchor (₹20,000 as of 1-Jan-2026).
Expected — after commit 7 new rows (nothing existed for this period before). Everything from Step 3 stays untouched and still verified — a clean backfill shouldn't disturb anything downstream, per the plan's own §10b "clean case" reasoning.

Step 4b — Optional: force the §14b disagreement variant

To see the DISAGREEING anchor-shift case instead: before importing, open hdfc-statement-jan-mar-synthetic.csv and change the first row's Credit from 35000 to 37000 (and its own Balance from 55000 to 57000) — a ₹2,000 difference that now carries through every later row's balance in that file (add 2,000 to each of the remaining 6 balances too, or just re-derive them). Re-import.

Expected The new anchor now implies ₹52,000 at 1-Apr-2026, disagreeing with the already-confirmed ₹50,000 by exactly ₹2,000 — you should see the three-choice disagreement screen (§14b), never an automatic resolution. This is the exact worked number from the main simulation doc's §14b, reproduced on-device.

Import hdfc-statement-jun-synthetic.csv into the HDFC account.

Expected 2 new rows: the ₹20,000 NEFT-out (no candidate exists yet — ICICI hasn't been imported — so it lands as a plain new expense) and a ₹5 NEFT fee (also new, genuinely one-sided, should never get confused with the transfer itself). Account stays verified. New running balance ₹1,59,325.

Step 6 — ICICI's first-ever import, closing the transfer loop

Create a new ICICI account (type bank), no opening balance set. Import icici-statement-jun-synthetic.csv — note its headers are deliberately worded differently (Txn Date/Withdrawal/Deposit/Closing Balance) to confirm column-mapping doesn't depend on any specific bank's exact wording.

Expected — first-import opening-balance prompt Same as Step 3: this is ICICI's first-ever bank-statement import. Suggested opening balance = ₹30,000 − ₹20,000 = ₹10,000, as of 1-Jun-2026. Confirm it.
Expected — the transfer suggestion (Stage 6) This row (₹20,000 credit, 10-Jun) should surface a "possible transfer" suggestion pointing at the HDFC expense from Step 5 (opposite direction, same date, same amount, different account). Accept it — both sides should now link as one type: 'transfer' record.
Expected — after commit ICICI account: verified, balance ₹30,000. HDFC account: still verified, balance unchanged at ₹1,59,325 (the ₹20,000 NEFT-out row, now converted to a transfer, still correctly debits HDFC — nothing about accepting the transfer suggestion should change HDFC's own total).

Step 7 — Specifically verify the transfer-checkpoint fix

This step exists purely to exercise the cross-contamination bug found and fixed after Stage 7 (see the plan's post-implementation fix entry) — a transfer whose both sides get independently bank-statement-imported used to risk one side's checkpoint silently overwriting the other's.

What to check Open HDFC's own checkpoint timeline (Stage 4's escape hatch) and confirm the 10-Jun transfer row's checkpoint still reads ₹1,59,330 (HDFC's own balance right after that transaction) — NOT ₹30,000 (ICICI's own balance), which is what the bug would have silently overwritten it with once ICICI's own import in Step 6 matched this same shared record. If HDFC's checkpoint shows anything other than ₹1,59,330 here, the fix has a gap — this is exactly the scenario it was written to prevent.
